## 0. 结论先行

- **算法主框架**：以 **OKVIS2 为主**（用其 `fullGraph` + `realtimeGraph` 实现实时回环 / 误差均摊 / 全局 BA），**Maplab 降级为夜间 / 后台优化兜底**。
- **核心矛盾**：Terramow 的所有产品优势（搬动恢复、立即保存、立即建多区 / 通道）根因都落在"实时建图、无显式优化等待"这一个点上；Eden 当前 Maplab 全图优化 5 分钟卡住了所有上层产品体验。
- **优先级目标**：建图过程中重定位 → 重定位后 VIO 续接 → 中断轨迹优化 → 板端 400 平 **2–3 分钟**优化 → 多帧重定位校验 → 与老地图持续关联。

## 1. 竞品功能分析（Terramow / 木星科技）

### 1.a 建图能力 & 模式


| 维度     | Terramow 实测                                                        |
| ------ | ------------------------------------------------------------------ |
| 建图轨迹   | **先弓字（边 = 机身宽），再自主沿边 2 圈**                                         |
| 建图模式   | 直接建图 / 割草建图（边割边建，弓字更密）                                             |
| 实时性    | **地图实时更新**（保存只需 ~10–20s，更像磁盘补写而非算法优化）；建完立即可割草                      |
| 断电存盘   | **建图过程中可断电存盘**，重启后未建完的图还在（推测关机指令前最后一次落盘，不一定实时存档）                   |
| 多区域    | 第一次建图只能单区域；建完后才能增删区域                                               |
| 通道     | 遥控到通道起点 → 机器原地转一圈（疑似重定位 / 打标）→ 遥控到终点 → 走建图逻辑；**支持最长 60m 通道**       |
| 显示行为   | 存在"细节版 / 平滑版"两种状态（保存时细节、运动中平滑 + 边界向内收缩）—— 推测是显示层逻辑，不是 VSLAM 真在重新优化 |
| 删除区域行为 | 删除 b 区后，b 位置仍能重定位成功；继续在删除的 b 区割草后会自动重新建出 b 区地图（疑似通道仍内部保留，未做完全清理）   |


#### 地图变化的实测截图

下图序列展示了 Terramow 在「建图完成 → 开始割草 → 小规模割草完成 → 保存 → 再次割草」过程中 APP 显示地图的变化：

1. 建图完成后 APP 显示，有更强的细节
2. 刚开始割草，地图突变，轮廓平滑并且边界缩小
3. 很小规模割草完成，出现更细节的轮廓，并且地图边界扩大
4. 割完后地图保存完成
5. 刚开始割草，地图突变，轮廓平滑并且边界缩小

1、3 对比：左下角边缘变化较大，其他地方细微变化

3、4 对比：只有左下角边缘变化

**关键观察**：Terramow 之所以能"任意搬动 + 立即保存 + 立即建多区"，根本原因是**没有显式的"建完图后再统一优化"过程** —— 这个能力是后续整个方案讨论的锚点。

### 1.b 重定位能力


| 场景      | Terramow 行为                                                |
| ------- | ---------------------------------------------------------- |
| 抱起后放回草坪 | 转圈 + 直行（不是穿插），重定位到老图                                       |
| 建图中搬动   | 自动定位中 → 前进 ~1m → 转随机角度（左右、圈数都不固定）→ 重定位后从当前位置继续，**不回原始位 a** |
| 重定位精度   | 相对关系准确，没有发现假成功                                             |
| 重定位频率   | **正常工作时几乎不主动重定位** —— 不跟丢、不遮挡就一直靠自身 VSLAM；仅遮挡 / 搬起触发        |
| 重定位用图   | **始终用已保存的老图**（搬桩测试可证：搬桩后位置错，重定位后回到老图坐标）                    |
| 局部图     | 推测有，但与老图交互很少（VIO + VSLAM 自身做得好）                            |
| 充电桩特征   | 充电桩搬动不影响重定位（不会去识别桩然后重定位）                                   |


**讨论中的反推**（哲哥 / 李宝玉）：

- 既然 Terramow 重定位也没明显计算代价，**为什么不一直频繁用？** —— 推测是它**自身 VSLAM 高频跟踪局部图**已经能很好约束 pose，所以不需要频繁挂载到老图上。
- 这也对应了 **odom 必要性**的讨论：如果 VSLAM 自身高频跟踪局部图能约束打滑，**odom 依赖可以减弱**（Terramow 怀疑没用 odom）。

### 1.c 业务逻辑


| 维度        | Terramow 实测                             |
| --------- | --------------------------------------- |
| 工作时间限制    | 完全按 **日出 / 日落** 时间硬限制（不是亮度）             |
| 时间缓冲      | 可设置日出后 / 日落前 0–2h 缓冲；默认日落前半小时、日出后半小时不工作 |
| 日落响应      | 持续检查；接近日落时机器主动停工并提示                     |
| 系统时间防护    | 修改手机系统时间不影响日出日落计算（机器端独立算）               |
| 动态障碍物     | APP 显示位置正确 → 有动态障碍物处理能力（视野占比有关，需要进一步定量） |
| 相机脏污 / 遮挡 | 已实现脏污检测 + 遮挡触发重定位                       |
| 出桩前遮挡     | 直接报错，机器退出基站                             |

## 2. 异常情况分析（Terramow vs Eden 当前状态横向对比）

> 这一节横向看异常 case 的处理；⚠️ 标注的是 Eden 必须解决但 Terramow 也没解决好的 corner case。

### 2.1 抗扰动（VIO 层面）


| 异常 case       | Terramow            | Eden 当前               |
| ------------- | ------------------- | --------------------- |
| 拖住轮子 / 按住轮子打滑 | **几乎不影响姿态**         | 引入 odom 才稳，否则 VIO 偶尔飞 |
| 推测原因          | 纯 VIO，或 odom 用极严格过滤 | odom 权重高              |


**讨论结论**：如果实时 VSLAM + 高频跟踪局部图能跑起来，odom 的权重可以降低；待实测 Eden 关 odom 后的打滑表现。

### 2.2 重定位类异常


| 异常 case   | Terramow                            | Eden 当前 / 期望             |
| --------- | ----------------------------------- | ------------------------ |
| 遮挡        | 立刻触发重定位（怀疑是按 VIO 跟踪点数量直接判定，非真正遮挡检测） | 类似策略                     |
| 长时间遮挡     | 未充分测试                               | 未充分测试                    |
| 搬起后放回     | 转圈 + 直行，重定位成功                       | 期望支持                     |
| 搬动后是否回原始位 | **不回**（从重定位位置继续）                    | **期望回原始位**（逻辑简单、不容易遗漏区域） |


### 2.3 边界 / 多区类异常 ⚠️


| 异常 case              | Terramow                      | Eden 期望          |
| -------------------- | ----------------------------- | ---------------- |
| **建图已完成 + 搬到完全无共视区** | **持续瞎走 5+ 分钟仍不报错**（不符合安规）     | 必须报错或停机          |
| **建图未完成 + 搬到新区**     | 没有重定位概念，以错误位姿当作扩展继续；APP 仍显示原区 | 必须支持中断后回到老区 / 报错 |
| 建图过程中搬到隔石板路的另一片草坪    | 测试未覆盖；理论上会分成两个未连接区            | 待定               |
| 删除 b 区后重定位           | 删除区还能成功；继续在删除区割草会自动重建         | 业务定义需对齐          |


### 2.4 ⚠️ 搬桩 corner case


| 操作                  | Terramow 行为           | 评价                               |
| ------------------- | --------------------- | -------------------------------- |
| 把"桩 + 机器"一起搬到错误位置出桩 | 以错误位姿一直走下去，**不主动重定位** | **重大隐患**：会出界；只在遮挡 / 搬起时才会触发重定位修正 |
| 单独搬桩                | 偶发性自行重定位回到老图          | 偶发，不可靠                           |


**Eden 期望**：建图与定位时**必须与老地图持续关联**（频率可降到 2–3s/次），避免每次坐标系都对不齐导致出界。这是与 Terramow 策略的关键差异点。

### 2.5 IMU 故障类（待验证）

- Terramow 疑似用 **TDK IMU**（与 360 同款，非高端）。8081 / 7081 一小时漂移可能就到 1°（李岩反馈）。
- 主要风险不是 BIAS 而是 **ACC 噪声 / MCU 抖动出异常值**。
- 加热补偿可考虑（板上加电阻预热到 CPU 稳定温度后再开机）。
- **结论**：只要 BIAS 不大、转一圈 360° 误差不超过 ±10°，VIO 跑得好就够，**不需要为 7081 付高额成本** —— 大幅降低供应链推动压力。

### 2.6 业务侧异常

- RTK 关闭后建图 30 分钟就飘走（杨倩侧反馈）—— VIO 不是无脑可信，**RTK 超时 1min 应触发重定位逻辑**。
- 现有 VIO 在大公字下表现 OK，但单纯摇一圈建图存在飘走风险。

## 3. 对 Eden 方案规划

### 3.a 建图

#### 3.a.1 主框架决策

**OKVIS2 为主，Maplab 兜底**。理由见会议讨论节选：

> 哲哥："如果它能持续做重定位，为什么不做？" —— 即如果 OKVIS 持续高频跟踪能跑通，重定位频率自然可以放低，所有产品体验都顺了。

#### 3.a.2 OKVIS2 官方回环代码拆解（李宝玉主讲）

OKVIS2 回环框架由两个 graph 协作：

`**realtimeGraph`（前端 / 实时线程）**

- 全局图存所有 KF，但只有一个 active window 可变，外部 fix。
- 找回环、校验回环。
- 局部 BA（仅 active window 内）。
- **误差均摊**：手算把回环误差（角度差 + 位置差）线性摊到回环圈内每帧上，**不走优化器**，因此非常快（简化版 PoseGraph）。
- 回环触发后：把老回环帧加入 active window 用其共视点参与 local BA，老帧本身 fix。

`**fullGraph`（后端线程）**

- 触发回环时做真正的全局 BA。
- 优化结果同步回 realtimeGraph。

~~**FinalBA**~~：所有数据完成后再做的最终 BA，实测耗时巨长 → **去掉**。

#### 3.a.3 候选思路对比（讨论中浮现）


| 思路                         | 提出 / 评价                                | 决策                        |
| -------------------------- | -------------------------------------- | ------------------------- |
| 思路 1：只用 realtimeGraph 误差均摊 | 速度最快；精度未必比 PoseGraph 差很多               | **优先尝试**                  |
| 思路 2：补上 fullGraph 后端全局 BA  | 慢但精度高；可考虑 ICE BA（增量式）                  | 后台跑可接受                    |
| 思路 3：增量 SBA / iSAM 类       | 适合"先弓字再沿边"（频繁回环）；不适合"先沿边一大圈"（一次回环跨度过大） | 与建图轨迹绑定                   |
| 用真正的 PoseGraph 替代误差均摊      | "考虑帧间相对位姿，结果应该比纯均摊更稳"（哲哥）              | 可在 realtimeGraph 阶段做或推到后台 |
| ~~走 Maplab 的 FinalBA~~     | "和现在刘博做的差不多了，不用考虑"                     | **否决**                    |


**李宝玉的进一步建议**：把"老帧"从 realtimeGraph 删掉，只放 fullGraph。好处：① 放后台容易存图；② 多线程冲突少。

#### 3.a.4 0114 方案细化

**方案 1（主推）：三件套并存**

- **Component**：重定位模块（沿用现 Maplab 重定位代码），持续输出当前帧到全局图位姿。
- **fullGraph**：位姿图，无 landmark；找到回环后触发后台姿态图优化（**两轮**）：
  - 第一轮：约束 = 重投影误差 + 位姿图边（含闭环约束 H × 100）+ IMU 边；变量 = 回环帧到当前帧 + 回环帧前 K 帧。
  - 第二轮：约束去掉闭环加权；其余同上。
- **realtimeGraph**：active window，闭环帧能恢复 landmark，做 VSLAM。

**方案 2**：建图只用 fullGraph，定位只用 Component，只重定位。
**方案 3**：建图 / 定位都用 fullGraph + VSLAM，加载已存 fullGraph。

**存图格式**：OKVIS 改用 **vimap / Google protobuf** 格式，与 Maplab 兼容；常变量分块存储。

#### 3.a.5 建图轨迹策略

- **优先"先弓字 + 再沿边"** —— 增量 BA / IMU 误差抵消优势更明显。
- 业务一致性：所有竞品（布查、Verza、激光机型）都是"先沿边 + 自主建图"，但激光不强调封闭环境，纯双目要在产品视觉上"显得智能"才跳过用户引导；这是产品诉求，技术上可"先弓字"。

#### 3.a.6 优化时间目标

- 当前 Maplab 全图优化 **5 分钟** → 目标 **2–3 分钟**（板端 400 平）。
- Maplab 持续作为后台 / 夜间优化器（"我们看起来响应非常快，第二天又有一张非常好的图"）。
- 后续可能挑选若干次密集弓字割草数据，做"无显式重建图，后台合并"。

### 3.b 定位

#### 3.b.1 主体策略

- 定位与建图共用同一套算法框架（OKVIS2）。
- **持续与老地图关联**（频率可降到 2–3s 一次），避免每次开机坐标系不对齐老图导致出界（这是与 Terramow 策略的关键差异）。
- 业务上正常工作时**不需要**像现在这么频繁挂载老图，但**不能完全不挂**。

#### 3.b.2 启动 / 加载流程

- 启动时自动加载已有地图。
- 加载后导航调用 重定位 / set_pose 接口才能开始工作。
- 建图完成后的地图更新策略 **待定**（选段轨迹更新？怎样避免 KF 堆积？）。

#### 3.b.3 抗打滑 / odom 处理

- 当前 odom 引入主因：早期 VIO 没 odom 偶尔飞。
- 如果 OKVIS2 高频跟踪局部图能稳定约束，odom 权重可降。
- **Action**：测试 Eden 关 odom 后打滑场景的实际严重度，对比 Terramow。

---

### 3.c 重定位

#### 3.c.1 建图过程中的重定位（核心目标）

- **目标**：建图未完成时也能在已有部分图上重定位。
- OKVIS：用其多会话功能（精度待测）。
- Maplab：实验过用未优化图重定位，**效果差**（成功率降低 80%，有提升空间但优先级降低）。
- 数据保存入磁盘的同时在内存中也保存（OKVIS → summary map），**保存后立即可用**。
- 触发重定位后，在已有地图上**继续存图**。

#### 3.c.2 重定位多帧校验

- 单帧 RANSAC 检测由建图模块负责。
- 重定位模块基于单帧结果做滑窗优化，把多帧 pose 拉一起做小优化，让最终 pose 更准。
- **当前问题**：单帧重定位假成功 / 跳变较大；地图中央区域成功率低（密集弓字情况下可见）。
- **设计时机**：当前问题排查完成后再统一设计。

#### 3.c.3 重定位完成后的续接

- 后续 VIO 定位数据要附加到已有建图数据上。
- OKVIS 中断轨迹优化：搬窗口靠相对姿态拉过去时跳变会很大，**需要中断点处理逻辑**。
- 预期风险不大（中间也有回环检测加约束，两条轨迹后续会持续找回环）。

#### 3.c.4 异常上报

- OKVIS 增加异常处理，**及时上报需要重定位**（VIO 跟丢 / RTK 超时 1min 等）。
- fullGraph 上调用重定位代码，避免假成功一直错下去。
