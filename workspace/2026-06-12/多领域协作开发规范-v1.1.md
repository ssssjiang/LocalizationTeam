## 一、文档目标

规范「涉及多领域的需求 / Bug」从**设计、开发、联调到合入 dev** 的全流程协作方式与分支策略，解决以下痛点：

- **接口漂移**：各领域各自开发，缺乏前期接口对齐，联调时才发现对不上
- **联调成本高**：缺少进入联调前的自测门槛，联调沦为找 bug 的地方
- **代码质量难把关**：Review 责任分散、标准不一，谁也不把关
- **责任不清**：谁主导联调、谁合入、谁 Review、Bug 归谁，靠口头约定
- **Bug 归属之争**：缺乏根因判定机制，易演变为主观指认与甩锅

## 二、适用范围

**强制**：任何**跨 ≥ 2 个领域**的需求开发或 Bug 修复（软件 / 算法 / 硬件 / 云端 / 测试等任一组合）。

**不适用**：

- 单领域内部开发（按各领域自身规范执行）
- 紧急 Hotfix（走单独的紧急修复流程）

## 三、角色与职责

角色与团队已有的 IPD / MDE 角色框架对齐：本规范的 Owner 即模块的 MDE（第一责任人），各领域代表即各领域 PL。

| 角色 | 对应 IPD 角色 | 关键职责 |
| --- | --- | --- |
| **Owner**（需求 / Bug 负责人） | **MDE（模块负责人 / 第一责任人）** | ① 牵头接口与方案评审；② 切 feature 分支；③ 主导联合联调；④ 组织联合 Review；⑤ 联调 + Review 通过后合入 dev；⑥ 作为 Bug 统一入口，判定根因与归属、协调解决与验收 |
| **各领域代表** | **PL（项目 / 技术负责人）** | 与 Owner **共担代码 Review 权限**，对本领域代码质量与架构一致性负责；Review 不通过有权打回；Review 僵持时担任仲裁人 |
| **相关开发人员**（各领域） | —— | ① 在 feature 分支上开发；② 可切个人 `feature_xxx` 分支；③ 完成本模块内部方案设计与研发自测；④ 完成开发后合入 feature；⑤ 修复联合 Review 发现的问题 |
| **SE（系统工程师）** | SE | 负责系统级需求拆解与技术方案设计，Owner 承接分解后的模块需求 |

## 五、流程步骤

### 5.0 设计与接口评审（切分支前）

1. **跨模块接口设计文档**：由 Owner(MDE) 牵头产出，明确各模块输入 / 输出 / 时序 / 异常约定；
2. **各模块内部方案设计**（即详细设计：模块内部的数据结构、算法逻辑、状态机、关键流程与异常处理）：各领域对本模块出方案，负责人(PL) 把关；
3. **测试用例设计与第 2 步内部方案设计并行启动**，不串行等待——边设计实现边设计怎么测，让测试视角在设计阶段就暴露边界 / 异常漏洞；测试项后续供软测设计黑盒用例参考；
4. **接口冻结**：接口确定后冻结，后续接口变更需在需求群同步，并触发受影响方重新评审；
5. 以上完成并经各领域 PL 确认后，方可进入 5.1。

### 5.1 切分支

涉及多领域的需求 / Bug，由 Owner 从 dev 分支上切一个 feature 分支。

### 5.2 分支开发

相关开发人员在 feature 分支上开发，同步完成本模块的**研发自测**（详见第六节）。

### 5.3 二级分支

开发过程中，开发人员可从 feature 分支再切出各自的 `feature_xxx` 分支。

### 5.4 联调

开发人员完成 A 类自测后合入 feature 做联合调试，联调由 Owner 主导；联调期间完成 B 类自测（详见第六节）。

### 5.5 联合 Review + 合入

联调完毕后，由 Owner 合入 dev。**合入前所有相关领域必须做代码评审（联合 Review）**。联合 Review 由 Owner(MDE) 与各领域 PL 共担，基线标准：

1. 功能正确性（对照设计文档与自测结果）；
2. 接口契约一致（与 5.0 冻结的接口一致）；
3. 代码风格符合各领域既定规范、无明显冗余；
4. 无引入新技术债（仓促补丁须标注 TODO 并登记）。

各领域可在此基线上叠加本领域 checklist。

## 六、研发自测要求

研发自测属**白盒测试**，与软测黑盒互补，覆盖内部状态、异常路径、边界条件与时序逻辑——这些风险很多只有实现者知道。自测项按是否依赖其他模块**分两类**，分别对应不同完成节点：

| 类别 | 定义 | 完成节点 |
| --- | --- | --- |
| **A 类：模块内自测** | 不依赖其他模块即可在本模块内验证的功能 / 逻辑 / 异常 / 时序 | **联调前必须全部通过**（准入联调的前置条件）|
| **B 类：联调依赖自测** | 必须等其他模块实现 ready 才能验证的逻辑 | **联调期间由研发完成**，仍属研发白盒自测，不甩给软测黑盒 |

自测项要求：

- 统一格式："测试项 - 操作步骤 - 期望结果 - 类别(A/B) - 是否通过"；
- 覆盖功能 / 逻辑 / 异常 / 时序四维度，做到不重不漏；
- 自测项后续提供给软测，作为黑盒用例设计参考。

> 说明：联调前只需完成 A 类，兼顾进度压力；B 类仍是研发白盒责任，避免"等黑盒兜底"。充分自测可减少软测 bug 量、节省查 bug 与复测时间、减少仓促打补丁引入的技术债。

## 七、多领域 Bug 处理流程

1. **统一入口**：所有软测 / 外测 Bug 由对应模块 Owner(MDE) 接收；
2. **根因与归属判定**：Owner 主导根因分析，按**根因**判定归属领域，而非按主观指认；判定需有日志 / 数据 / 复现支撑；
3. **分配与解决**：指派至对应领域，**从设计源头解决**，避免只治表面现象的无效打补丁；
4. **统一合入窗口**：Owner 协调多领域修复的合入时序，走联合 Review 后合入；
5. **闭环验收**：Owner 验收并更新 Bug 状态。

> 说明：归属按根因判定、由 Owner 统一裁定，把争议约束到流程内——主张需有根因 / 数据支撑，不以声量定责。

## 九、异常处理

| 异常场景 | 处理方式 |
| --- | --- |
| 联调失败 | Owner 协调定位问题域，问题分支 Owner 修复后重走合入 + 联调流程 |
| Review 不通过 | 对应领域开发人员修改，重提 Review（可批量 review 一次）|
| Review 僵持（Owner 协调无果）| 升级至 PL / 架构评审仲裁，48h 内给结论 |
| 合入冲突 | Owner 协调解冲突，联合 Review 通过后再合入 |
| 排期到点但准出未达标 | 不得静默豁免准出项；如需降标交付，由 Owner(MDE) + 各相关领域 PL **显式决策并记录**（降了哪项、风险、补齐时间），同步需求群 |
| Owner 请假 / 离职 | 需求群内指派新 Owner，同步更新需求 / Bug 系统 |
| feature 分支长期未合入（>2 周）| Owner 同步进展，确认是否需要 rebase dev |

## 十、准入与准出检查清单

### 10.1 准入（切 feature 分支前）

- [ ] 已识别涉及的所有领域
- [ ] Owner 已明确指定
- [ ] 跨模块接口设计文档已评审通过
- [ ] 各模块内部方案设计已由 PL 把关
- [ ] 测试用例设计已与内部方案设计并行启动
- [ ] feature 分支基于**最新** dev 切出
- [ ] 命名规范符合 `feature/<owner>-<topic>`

### 10.2 准入联调（开始联调前）

- [ ] 各领域 **A 类自测项全部通过**
- [ ] 相关 `feature_xxx` 个人分支已合入 feature

### 10.3 准出（合入 dev 前）

- [ ] 联合联调已通过（Owner 签字）
- [ ] 各领域 **A + B 类自测项全部通过**，自测文档三元素齐全
- [ ] 所有相关领域 PL Review 已通过
- [ ] CI / 自动化测试通过
- [ ] 需求 / Bug 状态更新

## 十一、质量内建与持续改进

- **质量内建闭环**：线上 / 外测问题复盘 → 根因转化为通用代码规范 → 加入 CI 检查项，形成沉淀；
- **根因导向修复**：Bug 与异常处理统一遵循先定位 root cause 再修，禁止只治症状；
- **轻量度量**：每迭代记录联调 bug 数 / Review 轮次 / delay 次数，作为规范迭代依据。

## 十二、与已有规范的关系

- **不替代**各领域自身的开发规范
- **不替代**代码提交、Commit Message 规范
- **不替代**CI / 测试准入规则
- **叠加使用**：在多领域场景下，于已有规范之上叠加本规范
- **角色框架**：引用《IPD 流程下 MDE 角色职责与流程》，Owner = MDE、领域代表 / 仲裁 = PL；本规范提供该框架下的分支策略、自测、联调与合入门禁的操作细则
