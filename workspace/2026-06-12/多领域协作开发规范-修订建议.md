# 《多领域协作开发规范》修订建议（v1.0 → v1.1）

> 提出人：宋姝（定位组）
> 面向：施敏杰（规范起草 / 研发负责人）
> 日期：2026-06-12
> 关联文档：《多领域协作开发规范 v1.0》、《IPD 流程下 MDE 角色工作职责与流程》、6/10「建图边界类型——研发自测」群聊共识

## 1. 总体建议

v1.0 把"合入门禁责任不清"解决得很好（§8.2 要求所有领域 Review 通过）。但它本质上是一份「**分支 + 合入流程规范**」，尚未覆盖协作全流程。建议 v1.1 按协作阶段补齐四块，并与团队已有的 IPD/MDE 角色框架对齐：

| 阶段 | 现状 | 本次补充 |
| --- | --- | --- |
| 前期 | 从"切分支"才开始，设计阶段为空 | 新增设计与接口评审，测试用例设计与各模块内部方案设计并行启动 |
| 过程中 | 无研发自测要求 | 研发自测进准入/准出，并按依赖关系**分层**（不一刀切）|
| 门禁 | 只说"联合 Review" | 定义 Review 基线 + 仲裁路径 + 进度↔质量决策机制 |
| 新增链路 | 无 Bug 处理流程 | 补"多领域 Bug 处理流程"，归属按根因判定 |
| 贯穿 | 仅"下次迭代"反馈 | 质量内建闭环（复盘→规范→CI）+ 根因导向修复 |

## 2. 角色对齐（与 IPD / MDE 框架）

团队已有《MDE 角色职责》文档，使用 IPD 标准角色（MDE / PL / SE / SPM）。本规范的自定义角色应与之对齐，避免一个团队两套角色语言。建议保留规范原术语、括号注明对应关系：

| 本规范角色 | 对应 IPD 角色 | 说明 |
| --- | --- | --- |
| Owner | **MDE（模块负责人 / 第一责任人）** | 功能/Bug/质量负总责；Owner 是制度角色，不是临时指派 |
| 各领域代表 | **PL（项目/技术负责人）** | 与 MDE **共担代码 Review 权限**，是质量与架构一致性防线，也是 Review 僵持的仲裁人 |
| —— | SE（系统工程师） | 负责系统级需求拆解，Owner 承接分解后的模块需求 |

## 3. 修订建议（按协作阶段逐条）

### 3.1 前期：新增"设计与接口评审"阶段

- **现状**：§5 从"切 feature 分支"开始，设计阶段为空。
- **问题**：跨领域联调成本高的根因常是**接口漂移**——各做各的，合时才发现对不上。
- **建议补充**（新增 §5.0）：

> **5.0 设计与接口评审（切分支前）**
> 1. 跨模块接口设计文档：由 Owner(MDE) 牵头，明确各模块输入/输出/时序/异常约定；
> 2. 各模块内部方案设计（即详细设计：模块内部的数据结构、算法逻辑、状态机、关键流程与异常处理）：各领域对本模块出方案，负责人(PL) 把关；
> 3. 测试用例设计**与第 2 步的内部方案设计并行启动**，不串行等待——边设计实现边设计怎么测，让测试视角在设计阶段就暴露边界/异常漏洞，测试项后续供软测设计黑盒用例参考；
> 4. 接口确定后**冻结**；后续接口变更需在需求群同步并触发受影响方重新评审；
> 5. 以上完成并经各领域 PL 确认，方可进入切分支。

- §8.1 准入清单增加：`[ ] 跨模块接口设计文档已评审通过`、`[ ] 各模块内部方案设计已由 PL 把关`、`[ ] 测试用例设计已与内部方案设计并行启动`。

### 3.2 过程中：研发自测进准入/准出 + 自测分层（重点）

- **现状**：§8.2 仅有"CI/自动化测试通过"，无研发自测；6/10 已达成的白盒自测共识未进规范。
- **问题**：
  - 不写进规范 → 自测变成"某人要求的"，无强制力，联调仍是发现 bug 的地方（摁下葫芦起来瓢）；
  - 但简单写"联调前必须自测完成" → **一刀切不成立**：部分逻辑必须等其他模块 ready 才能验证。
- **建议补充**：研发自测项按是否依赖其他模块**分两类**，分别对应准入/准出；两类都属研发白盒自测，区别于软测黑盒。

> **5.x 研发自测分层**
>
> | 类别 | 定义 | 完成节点 |
> | --- | --- | --- |
> | **A 类：模块内自测** | 不依赖其他模块即可在本模块内验证的功能/逻辑/异常/时序 | **联调前必须全部通过**（准入联调的前置条件）|
> | **B 类：联调依赖自测** | 必须等其他模块实现 ready 才能验证的逻辑 | **联调期间由研发完成**，仍属研发白盒自测，不甩给软测黑盒 |
>
> - 自测文档统一格式："测试项 - 操作步骤 - 期望结果 - 类别(A/B) - 是否通过"；
> - 覆盖功能 / 逻辑 / 异常 / 时序四维度，做到不重不漏；
> - 自测项后续提供给软测，作为黑盒用例设计参考。

- 清单修改：
  - **§8.x 准入联调（新增）**：`[ ] 各领域 A 类自测项全部通过`；
  - **§8.2 准出（合入 dev）增加**：`[ ] 各领域 A + B 类自测项全部通过`、`[ ] 自测文档三元素齐全`。

> 说明：联调前只需完成 A 类，回应了"功能急、工作量大"的合理诉求；B 类仍是研发白盒责任，堵住"等黑盒兜底"的口子。

### 3.3 门禁：Review 基线 + 仲裁 + 进度↔质量决策

#### 3.3.1 定义联合 Review 基线标准

- **现状**：只说"联合 Review"，未定义查到什么程度。
- **问题**：跨组摩擦原点——一方要"风格一致 + 简洁干净"，另一方认为"功能正常即可"，"Review 不通过"变成主观扯皮。
- **建议补充**（§5 第 5 步 / §3 职责）：

> 联合 Review 由 **MDE 与 PL 共担**，在功能正常基础上至少覆盖：
> 1. 功能正确性（对照设计文档与自测结果）；
> 2. 接口契约一致（与 §5.0 冻结的接口一致）；
> 3. 代码风格符合各领域既定规范、无明显冗余；
> 4. 无引入新技术债（仓促补丁须标注 TODO 并登记）。
> 各领域可在此基线上叠加本领域 checklist。

#### 3.3.2 Review 僵持的仲裁路径

- **建议补充**：Review 出现僵持且 Owner 协调无果时，升级至 **PL / 架构评审**仲裁，48h 内给结论。

#### 3.3.3 进度↔质量的决策与豁免

- **现状**：§7 处理了"长期未合入"，未处理"排期到了但质量没达标"。
- **建议补充**（§7 异常表新增一行）：

> | 排期到点但准出未达标 | 不得静默豁免准出项；如需降标交付，由 Owner(MDE) + 各相关领域 PL **显式决策并记录**（降了哪项、风险、补齐时间），同步需求群 |

### 3.4 新增链路：多领域 Bug 处理流程

- **现状**：v1.0 仅覆盖功能开发链路，无 Bug 流程。
- **问题**：跨组摩擦很大一部分是 **Bug 归属之争**（如互相指认"发错数据""改了需求"），缺乏判定机制时易演变为甩锅。
- **建议补充**（新增独立一节，与功能开发流程并列）：

> **多领域 Bug 处理流程**
> 1. **统一入口**：所有软测/外测 Bug 由对应模块 Owner(MDE) 接收；
> 2. **根因与归属判定**：MDE 主导根因分析，按**根因**判定归属领域，而非按主观指认；
> 3. **分配与解决**：指派至对应领域，**从设计源头解决**，避免只治表面现象的无效打补丁；
> 4. **统一合入窗口**：MDE 协调多领域修复的合入时序，走联合 Review 后合入；
> 5. **闭环验收**：MDE 验收并更新 Bug 状态。

> 说明：归属按根因判定、由 MDE 统一裁定，把"莫须有指责"约束到流程内——主张需有根因/数据支撑，不是谁声量大谁定责。

### 3.5 贯穿：质量内建闭环 + 根因导向

- **建议补充**：
  - **质量内建闭环**：线上/外测问题复盘 → 根因转化为通用代码规范 → 加入 CI 检查项，形成沉淀；
  - **根因导向修复**作为 Bug 处理与异常处理的统一原则（先定位 root cause 再修，禁止只治症状）；
  - **轻量度量**：每迭代记录联调 bug 数 / Review 轮次 / delay 次数，作为规范迭代依据。

### 3.6 次要项（视精力，可放下一迭代）

- 接口契约版本化：接口文档带版本号，变更触发重新联调；
- feature 分支长期未合入的 rebase 节奏（v1.0 §7 已有，建议明确周期）。

## 4. 配套改动提示
