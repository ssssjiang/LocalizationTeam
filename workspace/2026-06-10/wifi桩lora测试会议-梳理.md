## 1. 主题

桩 NRTK（WiFi 桩 + Lora 转发）方案能否替代 1+1 RTK 的测试评审。

- 背景：butchart s / monet pro / Gaia（盖亚）计划用「充电桩内置 NRTK + Lora 转发」替代标配的 1+1 RTK 基站。
- 目的（徐心恺明确）：核心不是降本，而是**免去用户自行安装 1+1 基站**这一步，提升产品竞争力；成本与 1+1 差不多。（次要论据：海外 4G 流量贵，桩可连用户家 WiFi 省流量。）
- 红线：**不能比 1+1 RTK 差**。本次会议判断当前测试数据是否触碰红线、方案是否可行。

## 3. 争议点

- **小丢包（毛刺）的根因**
  - 乔平平：桩位置放太低（离地仅 20–30cm，原 1+1 在 1.4–1.5m 杆上），电台信号弱导致，硬件优化空间不大。
  - 欧一文：小丢包大概率**不是 Lora 导致**——1+1 和 NRTK 都走 Lora，若是 Lora 问题 1+1 也该有；可能是 NRTK 下发或桩内转发问题，但**缺桩侧日志无法判断**。
  - 徐成：电台 2 秒一包、速率低，规律性小丢包不可避免，外场 SNR/RSSI 符合预期，属正常。

- **当前数据是否满足验收标准**（核心分歧：乔平平 vs 徐成）
  - 乔平平：按去年标准卡，**达不到**。
  - 徐成：卡丢包率没意义，应看长丢包；对角线穿墙（七八十米）实测已经很好，「这怎么不满足」。
  - 去年验收标准（定位 + 器件 + 供应商共定，主要源自导航毅超需求）：隔墙 50m、1 小时内 >5s 频次 ≤10、95% 数据 <5s、整体丢包率 <10%–15%。产品要求 200–300m，实际用户一般 <50m。

- **数据有效性**
  - 李威担心：测试样本里可能**一直跑的是主机 RTK 而非桩 RTK**（桩重启后切主机），若如此就「白测了」。
  - 赵一沣确认：部分锯齿数据确实是桩断后切主机、来回切换；有一段是主机和桩都用不上才出现超长丢包。

- **是否引导用户把桩放空旷处**
  - 乔平平：建议引导用户把桩放空旷处规避墙边问题。
  - 宋姝反对：用户就是倾向放屋檐下/墙角遮风挡雨，「卖出去这么久引导是失败的」，**必须墙角也一样好**。

- **质量下降能否接受**
  - 宋姝：没有降本却让器件表现变差，没有理由接受；要按器件变更评估流程走、要实事求是的结论，不能让用户直接承受定位质量下降（很可能导致用户家建图都建不成功）。

## 5. 达成一致的结论

1. **空旷 / 对角线场景（含七八十米穿墙）：NRTK 与 1+1 表现相当，OK。**
2. **墙边 / 遮挡场景：NRTK 比 1+1 差（丢包率约 20%）** —— 当前核心待确认问题，明天复测定论。
3. **长丢包（30s/60s/80%）基本判定为软件问题**（桩重启 / core），与硬件无关；侯振锟会后查日志、发群，桩重启后不可用的 bug **必须解决**。
4. 当前部分测试数据混入了主机 RTK，**需赵一沣先区分桩 RTK / 主机 RTK 才有效**，否则结论不成立。
5. 处理路径共识：**先确认墙边是否就是差 → 评估硬件是否有提升空间（乔平平、徐成倾向硬件几乎无空间）→ 评估软件能否兜底（宋姝：对「没数据」几乎无法兜，且不硬造）**。若硬件改不了、软件兜不住，则方案不可行；若下降幅度小且软件能兜，则项目继续。
6. **定位不接受直接拍板质量下降**，按「器件变更 / 降本质量变差导入」流程走，需动用测试人力做定量评估；宋姝可预判效果一定下降，但下降多少要测才能给定量结论。
7. **时间节点**：明天乔平平加测墙边数据，下午出结果即拉会复盘。
