第 4 章 构筑测试体系

主线：重构的前提是一套稳固的测试——即便有自动化重构工具，很多手法仍需测试保障。本章用一个 Province/Producer 业务逻辑示例，从第一个测试逐步搭到边界测试。 原书用 JavaScript + Mocha/Chai，本笔记把示例与测试改写成 C++ + GoogleTest（§8），并标注 JS 动态类型特有的坑在 C++ 里如何变化。 源：https://book-refactoring2.ifmicro.com/docs/ch4.html

1. 一页纸速查（本章 Tip 全集 + 决策规则）

1.1 核心 Tip（原书逐条）

  • 确保所有测试都完全自动化、让它们自己检查结果（全过只显示一个 OK，不用人眼盯输出）。
  • 一套测试就是一个强大的 bug 侦测器，大大缩减查找 bug 的时间。
  • 频繁运行测试：正在处理的代码，其测试至少每隔几分钟跑一次；每天至少全量跑一次。
  • 总是确保测试在不该通过时真的会失败（写完先故意引错、看它变红，再改回来）。
  • 编写未臻完善的测试并经常运行，好过对完美测试的无尽等待。
  • 若非法输入会让脏数据到处传播或产生很难调试的失败，可用引入断言(302) 让代码不满足预设时快速失败（失败断言本身是测试，不必再为它写测试）。
  • 每当收到 bug 报告，先写一个单元测试暴露这个 bug——测试通过才算修完。

1.2 决策规则（何时测、测什么、怎么组织）

决策点 规则
测什么 风险驱动：测「你最担心出错、逻辑复杂」的行为；不测只读写字段的简单访问器
测试粒度 观察类「应做的所有事」逐个行为测 + 边界，而非机械「测所有 public 函数」
测试结构 三种并列异名：配置-检查-验证（setup-exercise-verify）/ given-when-then / 准备-行为-断言（arrange-act-assert）+ 隐含的拆除(teardown)
断言数 一个测试最好一个验证语句；关系极紧密的断言可放一起，需要时再拆
测试夹具 用 beforeEach/SetUp 每个测试重建独立夹具；不要共享可变夹具（滋生按次序耦合的诡异 bug）
共享夹具 仅当创建慢且能保证夹具100% 不可变时才共享，并显式 teardown
边界条件 空集合、数值 0、负值、空字符串——把火力集中在「可能出错的边界」，扮演「程序公敌」
何时停（4.6） 边际效用递减；测试证明不了「无 bug」，但能抓住大多数 bug；集中在复杂/易错处
够不够（4.7） 无好的定量标准；主观信心（别人引入缺陷你多有把握揪出，不含盲目自信）+ 重构后全绿即够；过度测试信号：改测试比改代码更费时
覆盖率 只能识别「未被覆盖的代码」，不能衡量测试集质量
重构与红条 看到红条永不重构；出错就「回退到绿条」（撤销到上次全绿/版本控制提交点）

1.3 failure vs error（框架层面的重要区分）

  • failure（失败）：验证阶段实际值 ≠ 期望值——是你预期会检查的断言没过。
  • error（错误）：更早阶段（如配置阶段）抛出的异常——作者没预料到的异常场景。
  • 多数框架把两者分开显示；据此能快速判断「是断言不符」还是「代码在更早处就崩了」。

2. 自测试代码的价值（4.1）

  • 前提：编写优良测试能极大提高编程速度，即使不重构也如此（这违反很多程序员直觉）。
  • 观察程序员的时间分配：写代码只占少部分（还有决定下一步、做设计的时间），花在调试上的时间最多。修 bug 通常快，找 bug 才是噩梦；而且修一个常引入另一个，很久后才发现、又得重新定位。
  • 起源：1992 OOPSLA，据 Fowler 回忆「好像是」Bedarra 公司的 Dave Thomas 提出「类应该包含它们自己的测试代码」→ Fowler 把测试代码和产品代码一起放进代码库。
  • 关键跃迁：早期跑测试要把结果输出到控制台、人眼逐一检查，枯燥；作者「很懒」，于是让计算机来检查结果——把期望输出写进测试、自动比对，全过只显示一个 OK。代码从此能「自测试」。
  • 效应叠加：每次编译都跑测试 + 频繁运行 → 一旦引入被现有测试捕捉的 bug，因为「代码此前是绿的、上次测试就在不久前、代码量少记忆犹新」，几分钟就能定位（从前要一小时以上）。强大侦测力既来自代码能自测试、也得益于频繁运行。
  • 行为变化：意识到这点后不再等迭代结尾，写好一点功能就立即加测试、每天同步加，很少花超过几分钟追回归错误。
  • 工具史：1997 Kent Beck 与 Erich Gamma 在飞机上把 Smalltalk 测试框架移植到 Java，诞生 JUnit，催生各语言的 xUnit。
  • 推广难点：写测试要写额外代码；没体会到提速就觉得没意义；测试若需手动运行确实烦闷，能自动运行才有趣。
  • 最好时机：编码前先写测试——写测试即在问「为加这个功能我要实现什么」，把注意力聚焦接口而非实现，并给工作安上明确的结束标志（测试通过即完成）。
  • TDD（Kent Beck）：红（写一个失败测试）→ 绿（写代码让它通过）→ 重构的短循环，每小时循环很多次，带来高效有序的节奏。
  • 本书立场：重构需要测试——想重构就必须写测试；本章只教在 JS 里写简单测试，不是专讲测试的书，但少许测试往往就足以带来惊人收益。作者一边写代码一边写测试；遇到没测试的代码，重构前先改造成可自测试。

3. 待测试的示例代码（4.2）

  • 示例应用：查看/调整生产计划。每个行省（Province）有需求量 demand、采购价 price；若干生产商（Producer）各有成本 cost、产量 production。界面顶部还显示售出全部商品的总收入 full revenue，底部展示缺额（demand − 总产量）和总利润 profit；用户可改 demand、price、各生产商的 production 和 cost，改任一数值其他随之更新。
  • 只聚焦业务逻辑（算利润/缺额的类），从最简单、不碰 UI/持久化/外部服务的例子开始——「业务逻辑一复杂就与 UI 分离，便于理解和测试」这一隔离思路在任何场景都适用。
  • 两个类：Producer（基本是数据容器）、Province（构造函数吃一个可想象为 JSON 的对象，forEach 遍历 producers 逐个 addProducer）。设值函数被 UI 调用、接的是字符串，需 parseInt 转数值；get producers 返回的是副本（slice()）。
  • 埋点：Producer 的 production 设值函数里更新派生数据的方式有点丑陋（province.totalProduction += 新产量 − 旧产量），想重构——但重构前必须先加测试。
  • 核心计算：
  • shortfall = demand − totalProduction
  • profit = demandValue − demandCost
  • satisfiedDemand = min(demand, totalProduction)；demandValue = satisfiedDemand × price
  • demandCost：按 cost 从低到高排序，用 remainingDemand（初值 demand）逐个 contribution = min(remainingDemand, production)、递减并累加 contribution × cost。

4. 第一个测试（4.3）

  • 需要测试框架（JS 框架很多，作者选使用度/声誉都不错的 Mocha，只写例子不全讲）：describe 分组、it 写单个测试。一个测试两步：配置夹具（fixture：测试所需数据/对象）+ 验证特征。
  • 注意：4.3 的第一个测试夹具是在 it 块内内联构造（const asia = new Province(sampleProvinceData())），还没有 beforeEach（那是 4.4 才引入的组织方式）。
  • 运行反馈：在 NodeJS 控制台跑，正常时输出一串点 + 1 passing (61ms)（只含运行数/通过数）；故意引错后变 0 passing / 1 failing 并给出 AssertionError: expected -20 to equal 5。
  • describe/it 的描述信息：作者不喜多写，「够在失败时识别出对应测试」即可（认为描述性句子和注释一样是重复）。
  • 天然怀疑精神（尤其为既有代码、多测试并存时）：担心测试没按预期检查、出错时抓不到 → 想看每个测试至少失败一遍 → 暂时在被测代码里引入错误（如 get shortfall 里 * 2）看它变红、确认是自己引入的错误，再改回。
  • 框架会报告哪个测试失败 + 根本原因（实际值 vs 期望值）。
  • 断言库（Mocha 配 Chai）：assert 风格（assert.equal(x, 5)）与 expect 风格（expect(x).equal(5)）；作者理念上偏 assert，写 JS 时更常用 expect。
  • 真实系统可能有数千个测试，好框架应能简单快速运行、出错马上可见（反馈虽简单，对自测试代码尤为重要）。
  • 运行环境因环境而异：Java 用 IDE 图形化 runner（进度条，绿条/红条）；图形界面很棒但非必需，作者也常在 Emacs 快捷键看纯文本反馈——要点是能快速知道是否全过。
  • 红绿条口诀：「看到红条永不重构」（还有失败测试时先别重构）；「回退到绿条」（撤销最近改动、恢复到上次全过，通常切回版本控制最近提交点）。

5. 再添加一个测试（4.4）

  • 风格：观察被测类「应做的所有事」，逐个行为 + 边界条件测试。不是「测所有 public 函数」。
  • 风险驱动：目标是找现在/未来可能的 bug；不测那些只读写一个字段的简单访问器（太简单、不太可能错）。
  • 反直觉点：贪多反而测不充分——只做一点点测试也获益良多；把重点放在最担心出错的部分收益最大。
  • 第二个被测行为是总利润 profit（在同一夹具上加 expect(asia.profit).equal(230)）。
  • 为既有代码填期望值的最常用套路：先随便填一个期望值 → 跑出程序真实值（如 profit=230）填回（也可手动算，但既然代码在跑就暂时相信它）→ 再故意引入错误（乘 2）破坏、如预期失败才满意地 → 恢复错误。「先填 → 用真实值替换 → 引错 → 恢复」。
  • 测试夹具的重复：两个测试第一行都构造同一个 asia。作者对测试代码的重复同样怀疑，想提到一处消灭它。
  • 反例（// DON'T DO THIS）：把 const asia = new Province(sampleProvinceData()) 提到 describe 顶层共享——作者从不这样做。共享可变夹具会让测试互相影响：const 只保证引用不可变、对象内容仍可改；一旦某测试改了它，结果随运行次序变化 → 这是写测试时最恶心的 bug 之一，严重时动摇对整个测试体系的信心。
  • 推荐：let asia; beforeEach(() => { asia = new Province(...) })——每个测试前重建，保证独立性。
  • 性能顾虑：每次重建通常察觉不到差别；真慢且能确定夹具100% 不可变时才考虑共享。
  • 为何用共享的 beforeEach 而非把构造塞进每个 it：让读者熟悉公用夹具、把眼光聚焦到每个测试的不同之处；beforeEach 告诉读者「这些测试都基于同一套标准数据」。

6. 修改测试夹具（4.5）

  • 夹具在真实应用里会被频繁更新（用户改数值）。设值函数一般不测（不太可能出 bug），但 Producer 的 production 设值行为复杂、值得一测。
  • change production 测试模式：拿 beforeEach 的标准夹具 → 对夹具做必要的检查/修改（producers[0].production = 20）→ 验证期望行为（shortfall=−6、profit=292）。
  • 测试三段式的多种并列异名：配置-检查-验证（setup-exercise-verify）/ given-when-then / 准备-行为-断言（arrange-act-assert）。有时一个测试里见到全部步骤，有时早期公用阶段被提到 beforeEach 等标准配置里。
  • 隐含的第四阶段：拆除（teardown）——不那么明显、很少提及；移除夹具以确保测试间不交互。用 beforeEach 配置时框架默认在测试间自动拆除，等于免费享受（多数文献对它一笔带过、多数时候可忽略）；只有因创建缓慢等原因共享夹具时才需显式声明拆除。
  • 断言数原则：本例一个 it 里验证了两个不同特性（shortfall 与 profit）。基本规则是一个 it 最好只一个验证语句（否则第一个断言失败会掩盖后面的错误信息）；但本例两个断言关系紧密，放一起问题不大，需要时再拆。

7. 探测边界条件（4.6）

  • 之前都测「正常路径」（happy path）；还应把测试推到边界，检查出错时的表现。
  • 拿到集合就想看空集合：no producers（无生产商）→ shortfall=30、profit=0。
  • 数值类型的好边界是 0：zero demand（demand=0）→ shortfall=−25、profit=0。
  • 负值也值得：negative demand（demand=−1）→ shortfall=−26、profit=−10。
  • 引发思考：负需求 / 负利润在业务上有意义吗？最小需求不该是 0 吗？setter 是否该对负值特殊处理（抛错 / 归零）？——写边界测试帮你思考代码本应如何应对。
  • 空字符串：设值函数接的字符串来自 UI 字段（已限制只能填数字，但可能是空串）→ empty string demand 时 shortfall 和 profit 都应是 NaN。
  • 「程序公敌」心态：积极思考如何破坏代码，提高生产力也有趣。
  • failure vs error 的现场：string for producers（把 producers 传成 ""，期望 shortfall == 0）→ 结果不是断言不符，而是构造阶段抛 TypeError: doc.producers.forEach is not a function。概念上这属 error（更早阶段未预料的异常）；但 Mocha 仍把它报告为 failure，多数其他框架才会把它标为 error、与普通 failure 分开。
  • 该不该处理这种输入：
  • 处理：给更有意义的错误 / 把字段设成空数组（最好记日志）。
  • 维持现状：若输入来自可信数据源（同代码库另一部分），模块间加太多检查会造成重复的验证代码，弊大于利；但若来自外部服务（如返回 JSON 的请求），校验和测试就必要。
  • 重构相关：这种 error 测试若写在重构前，很可能删掉——重构只保证「可观测行为」不变，而这类异常已超越可观测范畴；删掉就不用担心重构改变了它的处理方式。
  • 何时停：任何测试都不能证明程序无 bug，但不影响「测试提速」；边际效用递减、贪多易气馁；集中在「代码变复杂、函数可能出错」处。开始重构前先确保有测试套件，前进途中还会不断加。不要因为测试无法捕捉所有 bug 就不写测试，因为它确实能抓住大多数 bug。

8. 测试远不止如此（4.7）

  • 定位：本书讲重构不是讲测试，但测试既是重构必要的基础保障、本身也是有价值的工具。
  • 本章展示的都是单元测试（测小单元、跑得快）——自测试代码的支柱、系统中占绝大多数；此外还有集成测试、跨层测试、性能测试等（同行对如何归类的争论比测试种类还多）。
  • 行业趋势：自第 1 版以来，测试的地位在转变——过去被当作「另一个独立团队的责任（且被认为所需专业技能也较少）」，如今成为每个开发者的必备技能；可测试性正成为衡量架构好坏的重要标准（好趋势）。
  • 测试是迭代活动：很难第一次写对；持续在测试集上工作（改测试、审视清晰度/价值）不亚于在主代码上。
  • 好习惯：遇 bug 先写测试复现，测试通过才算修完——测试存在一天，这个 bug 就不会再复现。
  • 多少算够：无好的定量标准；覆盖率只能找出「没被覆盖的代码」，不能衡量测试集质量。真正标准是主观的——「别人引入一个缺陷，你有多大信心测试集能揪出来」（盲目自信不算数）。自测试代码的全部目标就是帮你获得这种信心：重构完看到全绿、十分自信没引入新 bug，就算有了一套足够好的测试。
  • 过犹不及的信号：改测试比改代码花更多时间、能感到测试在拖慢你；但过度测试远比测试不足稀少。

9. C++ 视角：把示例与测试改写成 GoogleTest

用 GoogleTest 复刻原书 Mocha/Chai 示例。核心映射：describe→TEST_F 所属的 fixture 类；beforeEach→SetUp()；it→单个 TEST_F；expect(x).equal(y)→EXPECT_EQ(y, x)。

9.1 被测代码（Province / Producer）

#include <string>
#include <vector>
#include <memory>
#include <algorithm>

struct ProducerData { std::string name; int cost; int production; };
struct ProvinceData {
    std::string name;
    std::vector<ProducerData> producers;
    int demand;
    int price;
};

class Province;

class Producer {
public:
    Producer(Province* province, const ProducerData& d)
        : province_(province), name_(d.name), cost_(d.cost), production_(d.production) {}
    const std::string& name() const { return name_; }
    int  cost() const { return cost_; }
    int  production() const { return production_; }
    void setProduction(int amount);   // 更新派生数据 totalProduction —— 原书想重构的"丑陋"点
private:
    Province* province_;
    std::string name_;
    int cost_;
    int production_;
};

class Province {
public:
    explicit Province(const ProvinceData& doc)
        : name_(doc.name), demand_(doc.demand), price_(doc.price) {
        for (const auto& d : doc.producers)
            addProducer(std::make_unique<Producer>(this, d));
    }
    void addProducer(std::unique_ptr<Producer> p) {
        totalProduction_ += p->production();
        producers_.push_back(std::move(p));
    }
    const std::vector<std::unique_ptr<Producer>>& producers() const { return producers_; }
    int  totalProduction() const { return totalProduction_; }
    void setTotalProduction(int v) { totalProduction_ = v; }
    int  demand() const { return demand_; }
    void setDemand(int v) { demand_ = v; }

    int shortfall() const { return demand_ - totalProduction_; }
    double profit()  const { return demandValue() - demandCost(); }

private:
    int satisfiedDemand() const { return std::min(demand_, totalProduction_); }
    double demandValue() const { return static_cast<double>(satisfiedDemand()) * price_; }
    double demandCost() const {
        std::vector<const Producer*> sorted;
        for (const auto& p : producers_) sorted.push_back(p.get());
        std::stable_sort(sorted.begin(), sorted.end(),
                         [](const Producer* a, const Producer* b) { return a->cost() < b->cost(); });
        int remaining = demand_;
        double result = 0;
        for (const Producer* p : sorted) {
            int contribution = std::min(remaining, p->production());
            remaining -= contribution;
            result += static_cast<double>(contribution) * p->cost();
        }
        return result;
    }

    std::string name_;
    std::vector<std::unique_ptr<Producer>> producers_;
    int totalProduction_ = 0;
    int demand_;
    int price_;
};

void Producer::setProduction(int amount) {
    province_->setTotalProduction(province_->totalProduction() + amount - production_);
    production_ = amount;
}

ProvinceData sampleProvinceData() {
    return {"Asia",
            {{"Byzantium", 10, 9}, {"Attalia", 12, 10}, {"Sinope", 10, 6}},
            /*demand*/ 30, /*price*/ 20};
}

protected:

9.4 C++ 静态类型 vs JS 动态类型的坑

  • 原书的 empty string demand（NaN）和 string for producers（forEach is not a function 的 error）都源于 JS 动态类型 + 字符串输入。在 C++ 里分两种情况：
  • 类型不匹配（producers 传成字符串）→ C++ 编译期就报错，原书那个 error 场景根本不存在。这是静态类型消掉的部分。
  • 空字符串仍是运行时边界：UI 字段本就是字符串，C++ 通常在解析层用 setDemand(const std::string&) 内部 std::stoi + 异常处理。空串要测的是解析层行为（如抛 std::invalid_argument 或归零）——测点从 JS 的「NaN 传播」移到了「解析失败处理」，但仍需测。
  • 结论映射：静态类型把「类型不匹配」类非法输入从运行时 error 变成编译期错误；「合法类型但非法取值/解析失败」（空串、负数、越界）仍要在运行时测。
  • failure vs error 在 GoogleTest 的对应：EXPECT_* 不符 = 断言失败（failure）；SetUp/构造里抛未捕获异常或崩溃 = error——GoogleTest 同样把两者分开报告。

10. 给 SLAM / C++ 工程的落点

  • 风险驱动选测：优先给「派生数据更新」（如 §9 的 setProduction 更新 totalProduction_）、位姿组合、坐标变换、残差计算这类易错且被下游依赖的逻辑写单元测试；不给纯 getter/setter 写。
  • 独立夹具：SLAM 测试里常有「加载一段轨迹/一帧点云」的夹具，务必每个测试重建，别在 TEST 间共享可变的全局 map/state——否则测试次序会制造 flaky。
  • 边界火力：空点云、单点、共线/退化配置、0 视差、负时间戳、NaN/Inf 输入——正是 SLAM 里最容易崩的地方。
  • bug 先写复现测试：定位到重定位/建图 bug 后，先写一个能稳定复现的单测（固定输入 + 期望输出），修完变绿才收工。
  • 详细的 GoogleTest/CTest 约定见 cpp-testing skill。
