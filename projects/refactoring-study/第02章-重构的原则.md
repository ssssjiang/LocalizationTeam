# 第 2 章 重构的原则

> 本章是**纯理念章，几乎没有代码**。讲清楚「重构是什么、为什么、什么时候做、会遇到什么坑」，以及它和测试 / 持续集成 / 架构 / 性能的关系。
> 原书点名（未展开）的手法：提炼函数、改变函数声明、函数参数化、以多态取代条件表达式。本笔记给这些手法配 C++ 概念级片段。

## 0. 一页纸决策速查

**一句话**：重构 = 在**不改变可观察行为**的前提下，用**一连串微小且保持行为的步骤**，改善代码的可理解性、降低修改成本。它的**唯一目的是让你开发得更快**（经济驱动，不是道德/洁癖驱动）。

### 0.1 核心口诀

- **小步走**：每步都小到不会让代码进入「不可工作」状态；任何时刻能停、能回滚。
- **两顶帽子**：要么「加功能」，要么「重构」，**同一时刻只戴一顶**，心里始终清楚戴的是哪顶。
- **事不过三，三则重构**（三次法则）。
- **先让修改变容易，再做这次容易的修改**（Kent Beck）。
- **度量，别臆测**：性能问题永远先用 profiler 量，再优化。

### 0.2 何时重构（决策表）

| 触发场景 | 该不该重构 | 备注 |
|---|---|---|
| 要加新功能，但现有结构别扭 | ✅ 预备性重构 | 先铺路再加功能，更快 |
| 修 bug、找根因时发现重复/纠缠逻辑 | ✅ 预备性重构 | 让**这次修复**更容易，并降低复发 |
| 读不懂某段代码 | ✅ 帮助理解的重构 | 改名/拆函数，把理解写进代码 |
| 已懂代码、但发现写得差（好改） | ✅ 捡垃圾式重构 | 帮助理解的变体；「让营地比来时干净」 |
| 大型清理（换库/拆组件） | ⚠️ 长期重构 | 全队共识，逐步推进，别专设重构期 |
| 烂代码但**不需要改它** | ❌ 不重构 | 能藏在 API 之下就容忍 |
| 重写比重构还容易 | ❌ 改重写 | 需经验判断 |
| 大重构必要、但新功能很小 | ⚠️ 先加功能 | 偶尔的权衡，靠判断力 |

### 0.3 重构的前置条件（缺了就危险）

1. **自测试代码**：一套快速、可频繁运行的测试套件，是安全重构的基础。
2. **持续集成 / 主干开发**：让重构（尤其是广泛改名）的语义冲突尽早暴露。
3. 没测试时：只用 **IDE 自动化的、保证安全的重构手法**（如静态类型语言的改名）。

> 三大实践协同：**自测试代码 + 持续集成 + 重构**（后两者合流成 TDD），互相增效。

## 1. 何谓重构（2.1）

### 1.1 两个定义（名词 + 动词）

- **重构（名词）**：对软件内部结构的一种调整，目的是在**不改变可观察行为**的前提下，提高可理解性、降低修改成本。指那些「有名字的手法」（提炼函数、以多态取代条件表达式……）。
- **重构（动词）**：使用一系列重构手法，在不改变可观察行为的前提下调整结构。

> 一次「重构（动词）」可能花一两小时，其间用掉几十个「重构（名词）」。

### 1.2 关键特征：微小步骤

- **术语澄清**：过去十几年很多人把「重构」泛指任何代码清理；本书的定义是**一种特定的**清理方式——用大量微小且保持行为的步骤，一步步达成大规模修改。
- 每个单独的重构**要么本身很小，要么由若干小步骤组合而成**。
- 过程中代码**很少进入不可工作状态**；**即便重构没完成，也可在任何时刻停下来**。
- **判据**：若有人说重构期间代码一两天不可用，那他做的基本不是重构。
- 「结构调整（restructuring）」是泛称，重构是其中**保持行为**的一类。
- 为何小步反而更快：这些小步骤能**完美彼此组合**，而且整个过程**几乎不花时间调试**——所以「看似一大步能做完的事拆成小步」并不低效。

### 1.3 「可观察行为」的边界

- 原文措辞：整体而言，重构后代码做的事应与重构前**大致一样**；这个说法**并非完全严格，是故意留的空间**：
  - 提炼函数会改变调用栈 → **性能可能变**。
  - 改变函数声明 / 搬移函数 → **模块接口可能变**。
- 但**用户该关心的行为不变**。
- 已有 bug：重构后同样的 bug 应仍在（若是没人发现的潜在 bug，可顺手改掉）。

### 1.4 重构 vs 性能优化

- 相同：都改代码、都不改整体功能。
- **不同在目的**：
  - 重构 → 为了「更易理解、更易修改」，可能变快也可能变慢。
  - 性能优化 → 只为更快，最终代码**有可能更难理解和维护，且对此有心理准备**。

## 2. 两顶帽子（2.2）

Kent Beck 的比喻：开发时把时间分给两种**截然不同**的行为，且分清自己当前戴哪顶。

| 帽子 | 在做什么 | 能不能改既有结构 | 测试怎么处理 |
|---|---|---|---|
| **加功能帽** | 只加新功能 | ❌ 不改既有代码 | ✅ 加测试并让其通过，以此衡量进度 |
| **重构帽** | 只调结构 | ✅ 调整结构 | ❌ 不加任何测试（除非发现先前遗漏的东西）；只在**绝对必要**（处理接口变化）时才改测试 |

- 开发中会**频繁换帽**，典型两轮循环：
  - 想加功能 → 发现先改结构会让功能更容易加 → 换重构帽铺路 → 换回加功能帽；
  - 功能跑通后 → 发现自己的编码让程序难懂 → 再换重构帽整理。
- 整个来回也许只花 10 分钟，但任何时刻都清楚戴的是哪顶帽子，并明白**不同帽子对编程状态的不同要求**。

### 2.1 C++ 体会「换帽」

```cpp
// 加功能帽：原来只有一行计价，想加 VIP/节日折扣，发现要塞进一坨 if，先停。
double total = base * qty;   // 此步只跑现有测试，确认行为没变

// 换重构帽：先把计价逻辑提炼出来（不改行为，不加功能，不加新测试）
double basePrice(double base, int qty) { return base * qty; }

// 换回加功能帽：现在加折扣很容易（此步再补新功能的测试）
double finalPrice(double base, int qty, const Discount& d) {
    return d.apply(basePrice(base, qty));   // 新功能干净地接上去
}
```

## 3. 为何重构（2.3）

重构不是银弹，但是一把「银钳子」——帮你始终控制住代码。四个目的：

### 3.1 改进设计

- 没有重构，内部设计会**逐渐腐败**：只为短期目的、**没完全理解架构整体设计**就改代码 → 结构流失 → 越难看懂设计意图 → 越难保护设计 → 腐败越快（累积效应）。**经常性重构有助于代码维持该有的形态。**
- 设计欠佳的程序**往往需要更多代码**（同样的事在多处用相同语句做）；所以改进设计的重要方向：**消除重复代码**。
  - 重复的危害：同一件事在多处表述，改一处忘改另一处 → bug。
  - 「所有事物和行为只表述一次」是优秀设计的根本。
- 代码量减少不会让程序更快（对资源占用几乎无影响），但让**未来修改更容易**——代码越多越难做正确的修改。

### 3.2 更容易理解

- 编程是**与计算机对话**，核心在「**准确说出我想要的**」，填补「我想要它做什么」和「我告诉它做什么」之间的缝隙。
- 但源码除了计算机还有别的读者：**几个月后来读、来改代码的另一个程序员（很可能就是你自己）才是最重要的读者**。
- 重构让代码更易读、更清晰地表达意图。「我是个懒程序员，记不住自己写过的代码，所以把该记的东西写进代码里。」

### 3.3 帮助找 bug

- 「我承认我不太擅长找 bug。」但重构能**深入理解代码所作所为，并立即把新理解反映回代码**；搞清结构的同时**验证了对代码的假设** → bug 自然浮现。
- Kent Beck：「我不是特别好的程序员，只是一个有一些特别好习惯的还不错的程序员。」

### 3.4 提高编程速度（最终归宿）

- 前面一切都归结到这一点，虽反直觉但这是重点：**重构让你开发更快**。
- 两类团队对比：
  - **内部质量差**：一开始快，如今加功能越来越慢，越来越多时间用来想「怎么把新功能塞进现有代码库」，补丁摞补丁、要考古才能弄懂系统，bug 越修越慢，最后恨不得从头重写。
  - **内部质量好**：容易找到在哪改/如何改；良好模块划分让你只需理解一小部分；代码清晰则少引 bug、调试也容易；代码库逐步演化成**可快速构造新功能的平台**。
- **设计耐久性假说**：投入精力改善内部设计 → 软件「耐久性」增加 → 长期保持开发速度。作者声明**这是「假说」、无法科学证明，但他与认识的上百名优秀程序员的经验都支持它**。
- 20 年前行业陈规认为「设计必须在写代码前完成、之后只会腐败」；重构推翻了它：可以先做设计，再边改功能边持续改善。**预先做出良好设计非常困难，想既体面又快速地开发，重构必不可少。**

## 4. 何时重构（2.4）

> **三次法则**（Don Roberts）：第一次做就做；第二次做类似的事会反感但照做；**第三次再做，就该重构**。

绝大多数重构是**见机行事**的，融入日常编程流，不专门安排时间——「正如你不会专门安排时间写 if 语句」。

### 4.1 三种见机行事的重构

三者**触发状态不同，但有层级关系**：帮助理解（还不懂）→ 捡垃圾（已懂但写得差，是帮助理解的**变体**）；预备性则是为即将做的修改铺路。

| 类型 | 触发 | 做法 |
|---|---|---|
| **预备性重构** | 加功能前；或修 bug 找根因时发现结构障碍 | 先调结构让接下来的修改更容易（「先看地图找最快路径」——Jessica Kerr）。例：已有函数能满足大半需求、只是几个字面量不符 → 用**函数参数化**而非复制粘贴 |
| **帮助理解的重构** | 还读不懂代码、要先弄清它在做什么 | 改名、拆长函数，把脑中理解搬进代码（Ward Cunningham），再**运行软件检查理解是否正确**；小处变清晰后，会**看见之前看不见的设计问题**（Ralph Johnson「扫去窗上尘埃才看见风景」） |
| **捡垃圾式重构** | **已理解**代码，但发现写得不好（逻辑迂回 / 两个函数几乎相同） | 好改就马上改；难改就便笺记下、做完手头任务再回来。即便几个月后才清理完、每次不彻底，**代码也不会被破坏**。「让营地比来时干净」 |

### 4.2 有计划 vs 见机行事

- **肮脏代码必须重构，漂亮代码也需要很多重构**（写代码时的权衡——参数化到什么程度、函数边界划在哪——会随需求变化而过时）。
- **Kent Beck**：每次要修改时，**先令修改变容易**（警告：这件事有时会很难），然后再做这次容易的修改。加新功能最快的方法往往是先改现有代码使其容易加入；**软件永远不应被视为「完成」**。
- 有计划的重构应该**很少**：只有团队过去欠债、或某区域问题累积长大时，才专门花时间集中清理（在重构上花一周，会在未来几个月发挥价值）。
- 关于「把重构提交和功能提交分开」：好处是可**各自独立审阅批准**；但作者**不认同强制分开**——重构常与新功能紧密交织，分开反而丢上下文、看不出价值。各团队按需自己定，这不是毋庸置疑的原则。

### 4.3 长期重构

- 量级：大多数重构**几分钟到几小时**完成；大型重构（换正在用的库、把整块代码抽取成组件共享给另一团队、理顺一大堆混乱依赖）才可能要几周。
- 仍**不专设重构团队/重构期**：全队共识，谁靠近「重构区」就往目标方向推一点，系统始终可工作。
- 典型手法：**Branch By Abstraction**（先加一层抽象兼容新旧两套接口，调用方全切到抽象层后，再换掉底层）。

### 4.4 复审代码时重构 / 怎么对经理说 / 何时不该重构

- **复审时重构**：代码复审本身能传播知识、让有经验者带新人、帮更多人理解大型系统（我的代码对我清晰、对他人未必）。重构能让复审更进一步：边读边重构能真实「看见」建议落地后的样子，且**许多建议能立刻实现** → 复审结果更具体、更有成就感。三档体验：纯 PR 模式（作者不在场）效果不好 < 作者在旁边（提供上下文、认同意图）好很多 < 与原作者肩并肩边读边重构最佳（自然导向结对编程）。
- **怎么对经理说**（作者最常被问到的问题）：
  - 懂技术的经理 → 讲「设计耐久性假说」即可；这样的经理会鼓励日常重构、并留意「重构不够」的征兆（「重构过度」比「不够」罕见得多）。
  - 不懂技术、把重构当「弥补错误 / 不增值」的 → 作者给出有争议的建议：**别专门说**。理由：软件开发者是专业人士，经理只关心尽快交付，**怎么交付是程序员的事**；我领工资是因为擅长快速实现功能，而最快的方式就是重构。
  - （注：「别用整洁/道德论证、重构永远讲经济账」是 §5.1 的要点，见下。）
- **何时不该重构**：
  1. 烂代码**不需要改**、且能藏在 API 之下 → 容忍它丑。
  2. **重写比重构更容易** → 别重构（需经验判断）。

### 4.5 Branch By Abstraction 的 C++ 形态

```cpp
// 目标：把底层 OldLogger 换成 NewLogger，但调用方很多，不能一次性换

// 1) 先引入抽象层
struct ILogger { virtual void log(const std::string&) = 0; virtual ~ILogger() = default; };

// 2) 让旧实现适配抽象（系统照常工作）
struct OldLoggerAdapter : ILogger { void log(const std::string& m) override { old_log(m); } };

// 3) 调用方逐步改为依赖 ILogger，而非直接调 old_log()
void doWork(ILogger& logger) { logger.log("done"); }

// 4) 调用方全切到 ILogger 后，再加新实现并替换工厂，底层切换对调用方透明
struct NewLoggerAdapter : ILogger { void log(const std::string& m) override { new_log(m); } };
```

## 5. 重构的挑战（2.5）

任何技术都有取舍，重构也有 6 个常见挑战。

### 5.1 延缓新功能开发

- 最大阻力的误解：「重构拖慢进度」。回应：**重构的唯一目的就是开发更快**（更少工作量、更大价值）。
- 唯一真实需权衡的情况：大重构必要，但马上要加的功能很小 → 可先加功能（作者也说**很难描述和量化**这个判断，只能靠经验）。倾向重构的信号：能让新功能更易实现就一定做、问题见过几次、代码常被触碰；倾向不重构：很少碰、不常惹麻烦，或还没想清优化方向。
- 行业现状：**重构不足远多于重构过度** → 绝大多数人应多做重构（很多人体会不到，因为没在健康代码库上工作过）。
- 压制重构的不只是管理者，**程序员自己也常这么干**；有时程序员觉得不该重构，领导其实挺希望他们做。
- 技术 leader 责任：表明你重视代码库健康；给年轻人有意指导，加速他们积累「何时该/不该重构」的判断力。
- **别用道德论证**：拿「整洁代码 / 良好工程实践」当理由是陷阱；重构的意义是**纯经济考量**——加功能更快、修 bug 更快，**应永远由经济利益驱动**。

### 5.2 代码所有权

- 正面例子：能找到所有调用者时，**改变函数声明（124）** 可一次改完声明和全部调用点。
- 但很多手法会跨模块影响调用方。若调用方代码**由别的团队拥有（你没写权限）**、或是已发布给客户的 API，就难直接改。这类函数是**已发布接口（published interface）**：使用者与声明者彼此独立，**声明者无权改使用者的代码**——自作主张改一定会破坏使用者程序。
- 应对：改名时**保留旧声明转调新函数**（接口会变复杂，是避免破坏使用者的代价），旧接口标记为 deprecated，过段时间退休（有时得永久保留）。
- 所有制建议：**别搞细粒度强代码所有制**（每段代码唯一所有者）→ 接口维护成本爆炸（作者见过 3 人团队互相发布接口，直接改库本会简单得多）。推荐**团队代码所有制**：分工体现为**监控自己责任区的修改，而非禁止别人改**；跨团队可用「类开源模式」（在分支改别队代码、提交给对方审核），是「强所有制」与「混乱修改」两极端之间的折中。

```cpp
// published interface：不能直接删旧函数，保留薄包装转调新名
[[deprecated("use computeNetPrice")]]
double calcPrice(const Order& o) { return computeNetPrice(o); }  // 旧接口转调新接口

double computeNetPrice(const Order& o) { /* 真正实现 */ }
```

### 5.3 分支

- 特性分支拥趸的理由：保持主线不受未完成代码侵扰、保留清晰的功能版本记录、出问题易撤销。
- **特性分支**的缺点：隔离越久，集成（integrate）回主线越难；合并难度随分支寿命**指数上升**（存在 4 周的分支集成难度比 2 周**不止翻倍**）。频繁从主线 merge/rebase 只是缓解，几个人同时各开分支时并不能根治。
- 合并 ≠ 集成：
  - 合并（merge）：单向，主线 → 我的分支。
  - 集成（integrate）：双向，主线 ↔ 我的分支。
- 版本控制只懂文本、**不懂语义**：我改了函数名、Rachel 在她分支新增了对旧名的调用（**她集成前我看不见**）→ 集成后**编译/语义就坏了**。
- 重构尤其制造这类语义冲突（广泛改名）→ 用特性分支的团队常因此放弃重构。
- 推荐 **持续集成（CI）/ 主干开发（Trunk-Based）**：每人每天至少向主线集成一次。代价：主线要随时健康、大功能拆小、用**特性开关（feature toggle/flag）** 藏未完成功能。
- CI 与重构**天生互补**（Kent Beck 把两者一起放进极限编程）；用 CI 的团队软件交付更高效 [Forsgren et al]。
- 作者**并非**说绝不能用特性分支：足够短（一两天）就没大问题；开源项目（偶有不信任的提交者）可能合适；但对全职团队阻碍太大。即便没完全上 CI，也应**尽可能频繁集成**。

### 5.4 测试

- 重构「不改可观察行为」，但人总会出错 → 关键是**快速发现错误**。每个重构都是小修改，出错只需查**最后一步**；查不出原因就**回滚到版本控制最后一个可用版本**。
- 前提：一套**完备、运行快**的测试套件（慢就不愿频繁跑）。测试一挂，只需看上次成功后改的那几行。
- 自测试代码不只让重构可行，也让**加新功能更安全**（很快发现并干掉新引入的 bug）。
- 这正面回应「重构风险太大会引 bug」：没自测试代码时这担忧成立，所以才如此重视测试。
- 没测试的退路：
  - 只用 **IDE 自动化、保证安全的重构手法**，可不跑测试（会损失很多手法，但够用）。
  - 一个较新的流派：只用「经验证安全、特定于语言」的手法，能在测试覆盖很低的大型代码库上推进（行业了解还不足；参 Jay Bazuzi 讲 C++ 中安全运用提炼函数）。
- 自测试代码与 CI 紧密相关（靠 CI 捕获分支集成的语义冲突），是极限编程与持续交付的关键环节。

### 5.5 遗留代码

- 遗留代码的痛：复杂、缺测试、别人写的。
- 重构能帮理解遗留系统（改名、理顺结构），但**绕不开「没测试」这条恶龙**。
- 答案「没测试就加测试」说易行难、**没有简单解决办法**：可测的系统一开始就该考虑可测性（可那样它早就有测试了）。
- 最佳建议：读 Michael Feathers《修改代码的艺术》（出版十多年，建议仍管用）——**找接缝（seam），在接缝处插测试**，把系统纳入测试覆盖。制造接缝的重构本身有风险（无测试覆盖），此时安全的自动化重构是天赐福音。
- **就算有测试**，也别想一鼓作气把复杂混乱的遗留代码重构成完美；**每次触碰让它好一点**，越频繁使用的代码回报越高。

### 5.6 数据库

- 第 1 版说数据库是「重构常出问题的领域」，但**仅一年后**情况就变了：**Pramod Sadalage 的渐进式数据库设计** + **《数据库重构》（Ambler & Sadalage 共著）** 的方法已被广泛使用。
- 精要：**用数据迁移脚本，把数据库结构修改与代码一起提交、纳入版本控制**。要迁到某版本，就跑当前版到目标版之间的所有迁移脚本（改字段同改变函数声明（124）一样，找声明处 + 所有调用处，但旧数据也要转到新字段）。
- 同样**小步 + 每步完整**，每次迁移后系统仍能运行。
- 与常规重构不同：数据库重构最好**分散到多次生产发布**，便于回滚。
- 字段改名的安全套路 = **并行修改（Parallel Change / expand-contract，扩展-收缩）**：
  1. 加新字段（暂不用）；
  2. 写入逻辑**同时写新旧两个字段**；
  3. 读取逻辑逐个改读新字段；
  4. 观察一段时间无 bug；
  5. 删掉旧字段。

> 「并行修改 / expand-contract」是一个通用思想，不止用于数据库——任何「不能瞬间切换的接口替换」都可用：先扩展（新旧并存）、再收缩（删旧）。

## 6. 重构、架构与 YAGNI（2.6）

- 旧观念：架构必须在写代码前定死，之后只会腐败。重构推翻了它——**生产环境跑了多年的软件也能大幅改架构**。
- 重构对架构最大的影响：能得到一个**能优雅应对需求变化**的代码库。
- 「先把架构定死」的根本问题：**假设需求能预先充分理解**，但现实**多数时候**做不到——只有真正用过软件、看到它对工作的影响，人们才想明白要什么。
- 应对未来变化的办法**之一**是在软件里植入灵活性机制（如给函数预加十多个参数）；但它**不是免费午餐**：
  - 当前场景下变复杂；
  - **少考虑一个参数会让后面新添参数更麻烦**；
  - 经常猜错（需求没按预期变 / 机制设计不好）；
  - 反而拖慢响应变化的速度。
- **YAGNI**（You Aren't Going To Need It，你不会需要它）= 简单设计 / 增量式设计：与其猜未来要哪些灵活性，不如**只按当前需求构造软件、但把设计质量做高**；需求理解加深后再重构以应对新需要。
- **两条决策规则**：
  1. 不同调用者**不会传入不同参数值** → 就不要加这个参数（真要时用**函数参数化（310）** 也很容易）。
  2. 加灵活性会增加复杂度时 → 评估「**以后再重构有多难**」，只有未来重构很难才现在就加；不增加复杂度（如加几个命名良好的小函数）则乐意加。
- YAGNI ≠ 不做架构思考（确有人这样误用）；它是把架构/设计/开发融合的工作方式，**必须以重构为基础**才可靠。总有些时候缺少预先思考重构会难以开展，但平衡点已偏向「**先等一等，理解更充分再动手**」。延伸：演进式架构（Ford et al.）。

```cpp
// 反例：为「将来可能需要」预加一堆参数 —— 函数签名与实现因未使用的参数而臃肿、易猜错
double price(double base, int qty, bool vip, int holiday,
             double coupon, bool member /* ... */);

// YAGNI：先按当前需求写最简版
double price(double base, int qty) { return base * qty; }
// 真到「不同调用者要传不同折扣率」时，再用「函数参数化」加一个参数即可（见 §10.3）
double price(double base, int qty, double discountRate) {
    return base * qty * (1 - discountRate);
}
```

## 7. 重构与软件开发过程（2.7）

- 重构能否有效，与团队其他实践紧密相关。重构起源于**极限编程（XP）**——XP 融合了一组不太常见又彼此关联的实践（持续集成、自测试代码、重构）。XP 是最早的敏捷方法之一，曾引领敏捷崛起。
- **三大基石（强协同）**：
  1. **自测试代码**：一套能频繁运行的自动化测试，犯错就有测试挂掉（重要到作者专门用一章讲）；也是 CI 的关键环节。
  2. **持续集成**：每个成员需会重构且**不干扰他人**；CI 让重构快速分享，避免「这边在调接口、那边已删接口」，一次重构若影响别人**很快就会知道**。
  3. **重构**本身。
  > 后两者——**自测试代码 + 重构**——融汇成 **TDD（测试驱动开发）**；持续集成是与之并列的第三大实践。
- 三大实践与 YAGNI **双向增效**：**重构（及其前置实践）是 YAGNI 的基础**；YAGNI 又让重构更易（简单系统比塞满想当然灵活性的系统好改）。在它们之间找到平衡点 → 进入**良性循环**（代码既牢固可靠又能快速响应变化）。
- 再往上才谈得上**持续交付**：软件始终可发布（互联网团队可一天多次发布）；即便不需频繁发版，CI 也能降风险、按业务随时发版、**减少耗在 bug 上的时间**。
- 提醒：软件开发涉及人与人、人与机器的复杂交互，**说起来简单做起来难**；作者描述的方法已被证明能应对这种复杂性，但对使用者的实践和技能有要求。「敏捷」大多徒有其名——真敏捷要求团队在重构上**有能力、有热情**，且开发过程须与持续重构匹配。

## 8. 重构与性能（2.8）

> 核心结论：**先写「可调优」的软件，再在优化阶段定点调优**。重构短期可能让软件变慢，但让后期优化更容易，最终更快。
> 立场：作者**不赞成为设计纯洁性忽视性能**，也**不赌更快的硬件**（已有很多软件因太慢被弃用，硬件提速只略微放宽限制）。下面「先可调优再调优」是**除硬实时系统外**的普遍规则。

### 8.1 三种编写快速软件的方法

| 方法 | 做法 | 适用 |
|---|---|---|
| **时间预算法** | **分解设计时**给每个组件预分配时间 + 空间预算，绝不超支（**即便有组件间调度/预配机制也不行**） | 硬实时系统（如心律调节器，迟到的数据=错误数据） |
| **持续关注法** | 任何人任何时候都设法保持高性能 | 很常见、很诱人，但**通常没用**：为性能的改动多使程序难维护、拖慢开发；改善又分散、基于狭隘视角和对**编译器、运行时环境、硬件**的误解；即便真变快这点损失才值，可惜常事与愿违 |
| **90% 统计法** ✅ | 平时不特别关注性能，写构造良好的程序；进**优化阶段**（通常开发后期）再用 profiler 定点优化，对热点用持续关注法的手段打磨 | 绝大多数系统（企业信息系统等） |

### 8.2 90% 法的优化流程

1. 用**度量工具（profiler）** 找出真正消耗时间/空间的**性能热点**（一小段代码）。
2. 只集中优化热点，用持续关注法的手段去打磨。
3. 像重构一样**小步**：每步编译、测试、再度量；没提升就**撤销**。
4. 循环「发现热点 → 去除热点」直到客户满意。

### 8.3 两条关键事实

- **大半时间耗在一小半代码上**：一视同仁优化所有代码，90% 是白费（那些代码很少被执行）；**因缺乏对程序的清楚认识而花的优化时间都被浪费**。
- **度量，别臆测**（Ron Jeffries 的克莱斯勒综合薪资系统故事，支付过程太慢拖累测试）：
  - Kent / Martin / Ron **先凭全盘了解推测瓶颈、还凭空改设计** —— 一度量发现**全错**（那次 Kent 和 Martin 谢绝参加）。
  - 度量结果分两步：① 一半时间花在创建 **Date 实例**（值都重复，且创建经一段**无外部输入的字符串转换**，只因写起来简单）；② **追踪 Date 的用法**才发现它们多用于构造 **DateRange（起止日期）**，而绝大多数 DateRange 是**空的**。
  - 为「起始日在结束日之后」的构造不清晰，**先提炼出空区间工厂函数**；改清晰后**意外发现**可固定一个不可变空对象、让工厂始终返回它（享元）→ 速度近翻倍，只花 5 分钟。
  - 教训：**哪怕你完全了解系统，也要实际度量、不要臆测——臆测能让你学到东西，但十有八九是错的**。

```cpp
// 故事两步：先 Extract Function（空区间工厂），再 Introduce Flyweight（固定 kEmpty）。
// 关键：热点是「反复创建空区间」，所以只把【空区间】做成始终复用的单例。
class DateRange {
public:
    static const DateRange& emptyRange() {           // 工厂：始终返回同一个不可变空对象
        static const DateRange kEmpty{/*start*/1, /*end*/0};  // end < start ⇒ 空
        return kEmpty;                                // 不再每次 new
    }
    bool isEmpty() const { return end_ < start_; }
    // 非空区间是真正不同的值，照常按值构造；空区间一律走 emptyRange() 复用单例
    DateRange(int s, int e) : start_(s), end_(e) {}
private:
    int start_, end_;
};
```

> 两点助益（构造良好的程序对优化的帮助）：① **时间**——能更快加功能，就有更多时间投在性能上（准确度量保证投在恰当处）；② **粒度**——profiler 能把你带进更小的代码段，调整更容易、更清楚哪步起关键作用。

## 9. 起源 / 自动化 / 延展阅读（2.9~2.11）

### 9.1 重构起源（2.9）

- 作者曾想找「refactoring」一词的真正起源但失败了。重构不止于「清理代码」——本书把它视为**整个软件开发过程的关键环节**。
- **Ward Cunningham + Kent Beck**：80 年代用 Smalltalk 摸索出适合该环境的开发过程（即后来的 XP），意识到重构对生产力的重要性。Smalltalk 适合重构的原因：动态、**「编译-链接-执行」周期极短**（当时很多环境一次编译要花整晚）、面向对象、强工具、修改影响被隐藏在定义良好的接口背后。其思想让重构成为 Smalltalk 文化的重要元素。
- **Ralph Johnson**（UIUC 教授、GoF 之一）：揭示重构有助于开发灵活高效的框架。
- **Bill Opdyke**（Ralph 博士生，背景是电话交换系统）：从**工具构筑者**视角研究重构、看到它可用于 Smalltalk 之外的语言；对 **C++ 框架** 的重构手法感兴趣，研究「**语义保持的重构**」如何证明、如何用工具实现。其博士论文是该领域**第一部丰硕的研究成果**。
- **John Brant + Don Roberts**：开发第一个自动化重构工具 **Refactoring Browser**（得益于 Smalltalk 的环境）。
- 作者自述：1992 OOPSLA 初见 Bill 时觉得「有趣但没那么重要」，后来完全改观；因无书可推荐遂写下第 1 版。此后「重构」被行业广泛接受、走进程序员词汇库、工具涌现（尤其 Java），也带来「随意滥用该词」的副作用，但终归成了主流实践。

### 9.2 自动化重构（2.10）

- 工具简史：Smalltalk 的 **Refactoring Browser**（首个）→ 21 世纪初 Java（**IntelliJ IDEA** 最亮眼、IBM VisualAge 能力被 **Eclipse** 继承）→ C#（先 **ReSharper** 插件，后 **Visual Studio** 内置）。各工具/语言对自动化重构的支持高低不一。
- 两个层次：
  - **文本操作**（查找/替换式改名）：粗糙，做完必须重跑测试，但可作便捷起步（作者在 Emacs 里用宏加速）。
  - **语法树操作**：**更可靠地**保持行为，是「体面重构」的基础 → 依附原本就在语法树上做导航/静态检查的强大 IDE（还要能把改动写回编辑器视图，实现很有挑战）。
- **静态类型让很多手法更安全**（原书以 Java 为例）：如 `Salesman::addClient` 和 `Server::addClient` 同名，静态类型工具能精确识别该改哪个类的调用点，完全自动安全；动态类型（Smalltalk）只能列出所有调用点让你手工选 → 不安全、需重跑测试。
- 进阶工具：改名时连注释一起提醒改、提炼函数后找出重复片段建议替换——这是「用体面 IDE 而非死守文本编辑器」的理由。
- **信任边界**：IDE 菜单式重构通常可信任、往往不必立刻跑全套测试；但**反射调用**（如 Java `Method.invoke`）会迷惑不成熟的工具（成熟工具能较好应对），加上常间杂手动重构，所以仍应**经常跑测试**。
- **Language Server**：用软件生成语法树、给文本编辑器提供 API，让普通编辑器也能用上强重构（满足「想要 IDE 能力又想要文本编辑器灵活」的需求）。

## 10. 本章点名手法的 C++ 速记

本章只点名未展开，这里给最小 C++ 对照，建立第一印象（手法目录章会详讲）。

### 10.1 提炼函数（Extract Function）

```cpp
// 重构前：一个函数里混了「计算」和「打印」
void printOwing(const Invoice& inv) {
    double outstanding = 0;
    for (const auto& o : inv.orders) outstanding += o.amount;   // 计算
    std::cout << "outstanding: " << outstanding << "\n";        // 打印
}

// 重构后：把计算提炼成独立函数，意图更清晰、可复用、可单测
double calcOutstanding(const Invoice& inv) {
    double s = 0;
    for (const auto& o : inv.orders) s += o.amount;
    return s;
}
void printOwing(const Invoice& inv) {
    std::cout << "outstanding: " << calcOutstanding(inv) << "\n";
}
```

### 10.2 改变函数声明（Change Function Declaration）

```cpp
// 重构前：名字含糊
bool circum(double r);

// 重构后：改名 + 让参数表达意图（published interface 时保留旧名转调，见 §5.2）
double circumference(double radius) { return 2 * 3.14159 * radius; }
```

### 10.3 函数参数化（Parameterize Function）

```cpp
// 重构前：两个几乎一样的函数，只有字面量不同（重复代码）
double tenPercentRaise(Employee& e)  { return e.salary * 1.10; }
double fivePercentRaise(Employee& e) { return e.salary * 1.05; }

// 重构后：抽出差异为参数，合并成一个
double raise(Employee& e, double factor) { return e.salary * (1 + factor); }
// 调用：raise(e, 0.10) / raise(e, 0.05)
```

### 10.4 以多态取代条件表达式（Replace Conditional with Polymorphism）

```cpp
// 重构前：按类型分支的 switch/if（新增类型要改这里）
double payAmount(const Employee& e) {
    switch (e.type) {
        case Type::Engineer: return e.base;
        case Type::Manager:  return e.base + e.bonus;
        case Type::Sales:    return e.base + e.commission;
    }
}

// 重构后：把每个分支挪进子类的虚函数，消去条件分支
struct Employee { virtual double payAmount() const = 0; virtual ~Employee() = default; };
struct Engineer : Employee { double payAmount() const override { return base; } /*...*/ };
struct Manager  : Employee { double payAmount() const override { return base + bonus; } /*...*/ };
struct Sales    : Employee { double payAmount() const override { return base + commission; } /*...*/ };
```

## 11. 给 SLAM / C++ 工程的迁移提示

> 结合你日常工作（OKVIS/VIO/重定位/标定）的几个落点，便于把原则用起来：

- **预备性重构**：要给 VIO 加一种新传感器/新残差前，先把现有 factor 接口理顺，再加，比直接塞 if 快。
- **published interface**：对外的标定/重定位 API 改名时，用 `[[deprecated]]` 薄包装转调，别直接破坏下游。
- **度量别臆测**：优化 SLAM 前端/BA 性能前，先上 profiler（perf / VTune / gprof），别凭经验猜热点——和 §8.3 同理。
- **Branch By Abstraction**：替换某个数学库/求解器（如换 Ceres 版本/换线代后端）时，先抽 `ISolver` 抽象层，调用方切完再换底层。
- **自测试 + CI**：广泛改名（坐标系约定、变量命名）在没有 CI 的特性分支上极易语义冲突——这正是 §5.3 警告的场景。
