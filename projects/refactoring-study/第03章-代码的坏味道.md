# 第 3 章 代码的坏味道

> 本章由 Kent Beck 与 Martin Fowler 合写，是 24 种「坏味道」的清单：每种给出**识别信号 + 推荐的重构手法**。
> 定位：第 2 章讲「如何重构」，本章讲「**何时该重构**」——用「味道」这种直觉信号代替精确指标。
> 原书无 C++ 示例，本笔记给高价值味道配最小 C++ 片段。手法的「重构前→后」完整对照在第 6~12 章手法目录。
> 源：<https://book-refactoring2.ifmicro.com/docs/ch3.html>

---

## 0. 导言：为什么用「味道」

- Kent Beck 用「尿布臭了就换」比喻：与其给「何时重构」一个**精确衡量标准**，不如学会识别一些**迹象**——它们指出「这里有个可以用重构解决的问题」。
- 没有任何量度规矩比得上**见识广博者的直觉**：多少实例变量算太多、多少行算太长，要靠自己培养判断力。
- 用法：闻到味道 → 查下面的速查表 / 分节 → 看推荐手法能否帮上忙。所列条款未必与你的情况完全吻合，但能指引方向。

## 2. 命名 / 重复 / 规模

### 2.1 神秘命名（3.1）

- 整洁代码最重要的一环是**好名字**：深思熟虑给函数/模块/变量/类命名，使其清晰表明功能和用法。命名是编程中最难的两件事之一。
- 改名**可能是**最常用的重构：改变函数声明(124) 给函数改名、变量改名(137)、字段改名(244)。很多人不愿改名觉得不值得，但好名字能省下未来猜谜的大把时间。
- 改名不只是改标识符——关键洞察：**起不出好名字，往往说明背后有更深的设计问题**，为名字纠结常能推动代码精简。

### 2.2 重复代码（3.2）

- 总目标：在一个以上地点看到相同代码结构，设法合而为一程序会更好。危害：读时要逐份比对细微差异；改时要找出所有副本。
- 三档处理：
  - 同类两函数有相同表达式 → 提炼函数(106)，两处都调它。
  - 只是**相似不完全相同** → 先移动语句(223) 把相似部分挪到一起，再提炼。
  - 重复在同超类的不同子类 → 函数上移(350)，避免两子类间互相调用。

### 2.3 过长函数（3.3）

- 活得最长、最好的程序，函数都比较短；间接性带来的好处（阐释力、可分享、更多选择）都靠小函数支撑。函数越长越难理解。
- 现代语言已几乎消除函数调用开销。小函数确实带来「切换上下文」的负担，但现代开发环境能在调用处与声明处间快速跳转或同时显示；让小函数易懂的关键还是**良好命名**——好名字让人不必看实现。
- 原则：**每当想用注释说明什么，就把它提炼成一个以「用途」（而非实现）命名的函数**。哪怕调用比函数体还长也值得；就算只有一行、需注释说明也值得提炼。关键不在长度，在「做什么」与「如何做」之间的**语义距离**。
- 手法：99% 场合用提炼函数(106)；参数/临时变量阻碍提炼时用以查询取代临时变量(178)、引入参数对象(140)、保持对象完整(319)；还不行就上以命令取代函数(337)。
- 找「提炼哪段」的技巧：**找注释**（提示语义距离）；条件表达式用分解条件表达式(260)，switch 各分支提炼成函数、多处同条件 switch 用以多态取代条件表达式(272)；循环连同循环体提炼，难命名说明做了多件事 → 拆分循环(227)。

### 2.4 过长参数列表（3.4）

- 学编程时被教「所需的一切都通过参数传」（替代品是邪恶的全局数据），但参数太多也令人迷惑。
- 手法：能从一个参数查到另一个 → 以查询取代参数(324)；正从某数据结构里抽很多项 → 保持对象完整(319)；几项总同时出现 → 引入参数对象(140)；参数当行为开关 → 移除标记参数(314)。
- **用类可有效缩短参数列表**：多个函数共享同几个参数时引入类尤为有意义，用函数组合成类(144) 把共同参数变成类的字段（函数式视角：相当于造了一组「部分应用函数」）。

### 2.5 过大的类（3.20）

- 信号：想用单个类做太多事 → 字段太多 → 重复代码接踵而至；代码太多同样走向重复、混乱、死亡。
- 手法：把相关变量（如 `depositAmount` / `depositCurrency`，或同前缀/后缀的）一起提炼类(182)；适合做子类则提炼超类(375) 或 以子类取代类型码(362)（**其实就是提炼子类**）。类并非所有时刻都用到所有字段时，或许可**多次提炼**。
- 找拆分线索：观察**使用者**——若不同使用者各用一个功能子集，每个子集可拆成独立类。
- 类内代码多时也可先「内部消化」：5 个百行函数 → 5 个十行 + 10 个双行提炼函数。

### 2.6 冗赘的元素（3.14）

- 背景：程序元素（类/函数）能增加结构以支持变化、促进复用、或只是提供更好的名字；但有时不需要这层额外结构。
- 信号：函数名跟实现长得一样；类其实只是个函数（可能当初期望它长大但没等到，或重构后越缩越小、最后只剩一个函数）。
- 手法：内联函数(115)、内联类(186)；继承体系里用折叠继承体系(380)。

## 3. 数据相关

### 3.1 全局数据（3.5）

- 最刺鼻味道之一：**任何角落都能改、没有机制探测谁改的** → 诡异 bug、根源在遥远别处。全局变量、类变量、单例都算。
- 首要防御：封装变量(132)——用函数包起来，至少能看见/控制访问点；再把函数和数据搬进类/模块，**只允许模块内代码使用**以收窄作用域。
- 风险分级：**可被修改**的全局数据尤其可憎；若能保证程序启动后不再修改（需语言提供保证）则相对安全。
- 帕拉塞尔斯格言「剂量决定良药还是毒药」：少量全局数据无妨，越多处理难度**指数上升**；即便少量也愿封装——这是软件演进中应对变化的关键。

### 3.2 可变数据（3.6）

- 危害：改一处、另一处期望不同的数据 → 功能失效，罕见时更难查。函数式编程干脆「数据永不改变」（更新返回新副本）。
- 这类语言仍小众，但不可变性的优势值得借鉴——有很多办法约束更新、降风险：
  - 封装变量(132) 让更新都走少数几个函数；
  - 一个变量存了不同东西 → 拆分变量(240)；
  - 移动语句(223)+提炼函数(106) 把无副作用代码与更新代码分开；
  - 设计 API 用将查询函数和修改函数分离(306)；尽早用移除设值函数(331)（把设值函数的使用者找出来看看，顺带发现收窄作用域的机会）。
- 值能在别处算出来的可变数据尤其刺鼻 → 以查询取代派生变量(248)。
- 作用域几行内的可变数据问题不大，作用域越大风险越大 → 函数组合成类(144)/变换(149) 限制可改它的代码量；内部含数据则用将引用对象改为值对象(252) 整体替换而非改内部。

### 3.3 数据泥团（3.10）

- 信号：几项数据（两项也算，不限三四项）总结伴出现（两个类的相同字段、多个函数签名的相同参数）。
- 手法：字段形式出现处用提炼类(182)；函数签名处用引入参数对象(140)/保持对象完整(319)，直接好处是缩短参数列表、简化调用。**新对象哪怕只用上一部分字段，只要替掉 ≥2 个字段就值得**。
- **判定技巧**：删掉其中一项，其余是否就失去意义？失去 → 它们该成为一个新对象。
- 提倡新建**类**（而非简单记录）：有了类就能进一步找「依恋情结」、指出能移进去的行为——有用的类被创建、大量重复被消除、后续开发加速。

### 3.4 基本类型偏执（3.11）

- 背景：很多程序员不愿创建对问题域有用的基本类型（钱、坐标、范围）→ 把钱当普通数字算、无视单位（英寸+毫米）、满屏 `if (a < upper && a > lower)`。
- 字符串是重灾区："电话号码不只是一串字符"，体面的类型至少能包含一致的显示逻辑（UI 显示时用）；这种 "stringly typed" 变量太常见。
- 手法：以对象取代基本类型(174)；若是控制行为的类型码 → 以子类取代类型码(362)+以多态取代条件表达式(272)；一组总同现的基本类型是**数据泥团征兆** → 提炼类(182)/引入参数对象(140)。

### 3.5 纯数据类（3.22）

- 信号：拥有字段 + 字段访问函数、**除此一无长物** → 「不会说话的数据容器」，几乎一定被别的类过分细琐地操控；行为放错了地方。
- 手法：public 字段尽快封装记录(162)；不该被改的字段用移除设值函数(331)；**找出取值/设值函数被其他类调用的地点**，把那些行为搬移函数(198) 进来（整函数搬不动就先提炼函数(106) 产生一个可搬的）。把行为从客户端搬进来就能大为改观。
- **例外**：作为**函数调用返回结果**的中转记录（如拆分阶段(154) 的产物）——它**不可修改**（至少在拆分阶段实际操作中如此），不可修改的字段**无须封装**，使用者直接通过字段取数、无须取值函数。

## 4. 变化的形状（修改困难）

> 发散式变化与霰弹式修改是**一对相反**的味道，都违背「改一件事只在一处改」。

### 4.1 发散式变化（3.7）

- 信号：**一个模块**因不同原因、在不同方向上反复变化（「加数据库要改这 3 个函数；加金融工具要改那 4 个」）——数据库交互与金融逻辑是两个不同上下文，挤在了一个模块。
- 目标：把两个上下文分到**各自独立的模块**，每次改一个上下文时只需理解这个上下文。手法：
  - 两方向有自然先后（先取数据再算逻辑）→ 拆分阶段(154)，中间用清晰数据结构沟通；
  - 来回调用多 → 先建模块再搬移函数(198)；函数内混了两类逻辑 → 先提炼函数(106) 再搬；类形式 → 提炼类(182)。
- 注意：上下文边界常**要等加了新数据库/新工具才显现**，早期不清晰是正常的。

### 4.2 霰弹式修改（3.8）

- 信号：**一种变化**要在许多不同的**类**里做许多小修改——散布四处、难找全、易漏改。
- 手法：搬移函数(198)/搬移字段(207) 把要一起改的代码归入同一模块；相似数据操作用函数组合成类(144)、转化/充实数据用函数组合成变换(149)；一些函数的输出可组合后提供给一段专门使用这些结果的逻辑 → 拆分阶段(154)。
- 反向策略：用内联函数(115)/内联类(186) 把本不该分散的逻辑**拽回一处**；内联后可能闻到「过长函数/过大类」，再用提炼手法拆成合理小块——即便钟爱小型函数和类，重构中途**暂时**造大单元也不必担心。

### 4.3 重复的 switch（3.12）

- OO 布道者立场：任何 switch 都该用多态消除，甚至绝大多数 if 都该进历史垃圾桶。作者并不认同——**从未无条件反对条件语句**。
- 历史：第 1 版叫「switch 语句」，因 90 年代末程序员太忽视多态而矫枉过正；如今多态用得多了、很多语言的 switch 也更强（不只按基本类型值判断），不再一概有害。
- 现在关注的是**重复的 switch**：同一条件分支逻辑（switch/case 或连续 if/else）散在多处 → 每加一个分支都得找全所有 switch 逐一更新。
- 手法：以多态取代条件表达式(272)。

## 5. 耦合 / 职责错位

### 5.1 依恋情结（3.9）

- 模块化目标：最大化区域内交互、最小化跨区域交互。信号：某函数与**另一模块**的数据/函数交流远多于自己模块（为算一个值调了人家半打取值函数）。
- 疗法：搬移函数(198) 把它移过去；只有一部分依恋 → 先提炼函数(106) 再搬。
- 函数用到多个模块时：放到**拥有它所用数据最多**的那个模块；先用提炼函数(106) 把它分解为数个较小函数分别置放会更容易。
- 例外：GoF 策略模式、访问者模式、Beck 的 Self Delegation——它们**故意**违反，为对抗发散式变化（隔离少量待覆写行为，代价是多一层间接）。最根本原则：**总是一起变化的东西放一块**——数据与其行为通常共变；若不共变，就搬移那些行为，让变化只在一处发生。

### 5.2 过长的消息链（3.17）

- 信号：`a.getB().getC().getD()` 一长串导航（实际可能是一长串取值函数，**也可能是一长串临时变量**）→ 客户端与中间导航结构**紧密耦合**，关系一变客户端就得改。
- 手法：隐藏委托关系(189)（可在链的不同位置用，但全用会把中间对象都变「中间人」）。**通常更好**的做法：看链末对象用来干嘛 → 用提炼函数(106) 把使用它的代码提炼出来，再搬移函数(198) 推入链中；若还有许多客户端要访问链上其他对象，同样添加函数完成。
- 态度：作者不认为所有函数链都是坏的（「我们的冷静镇定是出了名的」）。

### 5.3 中间人（3.18）

- 前提：对象的基本特征之一是**封装**——对外隐藏内部细节，封装往往伴随委托（问主管时间，他委托给记事簿，你不必知道他用什么记）。
- 信号：人们**过度委托**——一个类一半接口都在转发——就是味道。
- 手法：移除中间人(192) 直接跟真正负责的对象打交道；只有少数转发函数 → 内联函数(115) 放进调用端；中间人还有其他行为 → 以委托取代超类(399)/子类(381)，这样既能扩展原对象行为，又不必负担那么多委托。

### 5.4 内幕交易（3.19）

- 背景：开发者喜欢在模块间建高墙、反感大量交换数据（增加耦合）；一定的交换不可避免，但要**尽量减少并放到明面上**。
- 信号：模块间「在咖啡机旁窃窃私语」——私下大量交换数据。
- 手法：搬移函数(198)/搬移字段(207) 减少私下交流；有共同兴趣则新建模块放共用数据，或用隐藏委托关系(189) 让一方做中介。
- 继承尤其易「密谋」（子类对超类了解总超过后者的主观愿望）→ 想让孩子独立就以委托取代子类(381)/超类(399) 离开继承体系。

## 6. 继承相关

### 6.1 异曲同工的类（3.21）

- 类的好处之一是可替换（今天用这个类、未来换成另一个），但前提是**接口一致**。信号：两类做同样的事，接口却不同。
- 手法：改变函数声明(124) 对齐签名；这往往不够，反复搬移函数(198) 把行为移入类中、直到协议一致；搬移造成重复 → 或许用提炼超类(375) 补偿。

### 6.2 被拒绝的遗赠（3.23）

- 信号：子类继承了超类的函数/数据，却不想或不需要（「拿到所有礼物，只挑几样玩」）。
- 传统说法（略带贬义）：继承体系设计错了 → 建兄弟类，用函数下移(359)/字段下移(361) 把用不到的推下去，超类只留共享部分（「所有超类都该是抽象的」）。
- **作者立场（重要细节）**：不建议每次都这么做。用继承复用行为在日常工作中很好用；这味道通常**很淡、十有八九不值得理睬**，只有在引起困惑/问题时才按传统忠告办。
- 关键区分：子类**拒绝继承超类实现**作者不介意；但若**复用了超类实现却拒绝支持超类接口** → 味道变浓烈，应以委托取代子类(381)/超类(399) 彻底划清界限。

## 7. 过度设计 / 过时风格

### 7.1 夸夸其谈通用性（3.15）

- 命名者 Brian Foote。信号：「总有一天会需要」→ 加各种**钩子和特殊情况**处理非必要的事 → 更难理解维护。**会用到才值得，用不到就搬开**。
- 手法：没用的抽象类用折叠继承体系(380)；不必要的委托用内联函数(115)/内联类(186)；未用的参数/为未来塞的参数用改变函数声明(124) 去掉。
- 特例：函数/类的**唯一用户是测试** → 先删测试用例，再移除死代码(237)。

### 7.2 临时字段（3.16）

- 信号：字段仅为某种特定情况而设，多数时候不参与逻辑 → 读者以为对象总需要所有字段，在字段未被使用时猜测其用途让人发疯。
- 手法：提炼类(182) 给这些字段一个家，搬移函数(198) 把相关代码搬进去；也许还可用引入特例(289) 在「变量不合法」时给个替代对象，避免条件式代码。

### 7.3 循环语句（3.13）

- 信号：显式循环（不限 for）——循环从最早的语言起就是核心要素，但作者觉得它已过时（「像喇叭裤和植绒壁纸」）。第 1 版时就想替换，只是当时 Java 没有更好替代品。
- 手法：函数成为一等公民后，用以管道取代循环(231) 让循环退休——filter/map 等管道操作更快看清「处理哪些元素 + 做什么动作」。

### 7.4 注释（3.24）

- 澄清：**不是说不该写注释**——从嗅觉上说注释不是坏味道、反而是香味；提它是因为人们常拿它当「**除臭剂**」：一段代码有长长的注释，往往是因为代码很糟糕。
- 用法：注释能引你找到其它味道 → 先重构去除味道，完成后常发现代码已清楚说明一切、注释就多余了。
  - 需注释解释「做什么」→ 提炼函数(106)；提炼后仍需注释解释行为 → 改变函数声明(124) 改名；注释说明需求规格 → 引入断言(302)。
- **Tip：想写注释时，先尝试重构，试着让所有注释都变得多余。**
- 注释的**正当用途**：不知道该做什么时；记录「将来打算」；标记没把握的区域；写下「**为什么**这么做」（帮将来健忘的修改者）。

## 8. C++ 视角：几种高价值味道的最小示例

> 只挑「换成 C++ 后差异明显」的味道。提炼函数/改变函数声明等基础手法见第 2 章 §10。

### 8.1 基本类型偏执 → 以对象取代基本类型（3.11）

```cpp
// 味道：用 double 表示钱，单位/精度全靠程序员自觉，易把人民币和美元相加
double price = 9.9;

// 疗法：造一个领域类型，把约束和行为收进来
class Money {
public:
    Money(long long cents, std::string ccy) : cents_(cents), ccy_(std::move(ccy)) {}
    Money operator+(const Money& o) const {
        if (ccy_ != o.ccy_) throw std::invalid_argument("currency mismatch");
        return Money{cents_ + o.cents_, ccy_};
    }
    std::string toString() const;   // 一致的显示逻辑
private:
    long long cents_;               // 用整数分避免浮点误差
    std::string ccy_;
};
```

### 8.2 数据泥团 / 过长参数列表 → 引入参数对象（3.10 / 3.4）

```cpp
// 味道：start/end 总是结伴出现在每个签名里
bool   overlaps(int s1, int e1, int s2, int e2);
double length(int start, int end);

// 第一步「引入参数对象」：把结伴数据收成一个对象，函数签名仍是自由函数、只是参数变少
// （删掉一项另一项就失去意义 ⇒ 该成对象）
struct Range { int start, end; };
bool   overlaps(const Range& a, const Range& b);
double length(const Range& r);

// 可选的第二步：发现这些自由函数其实只依恋 Range 的数据（依恋情结）⇒ 再「搬移函数」进类里
struct Range2 {
    int start, end;
    bool   overlaps(const Range2& o) const { return start <= o.end && o.start <= end; }
    double length() const { return static_cast<double>(end - start); }
};
```

### 8.3 重复的 switch → 以多态取代条件表达式（3.12）

```cpp
// 味道：同一个 type 在多处 switch，新增类型要改所有 switch
double payAmount(const Emp& e) {
    switch (e.type) { case ENG: return e.base; case MGR: return e.base + e.bonus; /*...*/ }
}
double vacationDays(const Emp& e) {
    switch (e.type) { case ENG: return 20; case MGR: return 30; /*...*/ }   // 又一个同样的 switch
}

// 疗法：每个类型一个子类，行为各自覆写，新增类型只加一个类
struct Emp { virtual double payAmount() const = 0; virtual int vacationDays() const = 0; virtual ~Emp() = default; };
struct Engineer : Emp { double payAmount() const override; int vacationDays() const override; };
struct Manager  : Emp { double payAmount() const override; int vacationDays() const override; };
```

### 8.4 过长的消息链 → 隐藏委托关系（3.17）

```cpp
// 味道：客户端被迫知道 person → department → manager 的导航结构
Person* mgr = person.getDepartment()->getManager();

// 疗法：在 Person 上加一个委托函数，客户端不再关心中间结构
class Person {
public:
    Person* manager() const { return dept_->getManager(); }   // 隐藏委托
private:
    Department* dept_;
};
Person* mgr = person.manager();
// 注：隐藏委托是消息链的手法之一；原书「更常」先看链末对象用途，用提炼函数+搬移函数推入链（见 §5.2）。
```

### 8.5 中间人 → 移除中间人（3.18）

```cpp
// 味道：如果 Person 把一大半接口都这样转发给 Department，就成了"中间人"
// 疗法（按转发占比/是否另有行为分档，注意与 3.17 消息链是两种不同味道）：
Department* dept = person.department();   // ① 过半接口都在转发 → 移除中间人：暴露真正负责的对象
// ② 只有少数"不干实事"的转发函数 → 内联函数(115)，把转发体内联进调用端
// ③ 中间人还有其他实质行为 → 以委托取代超类(399)/子类(381)，变成真正的对象
```

## 9. 给 SLAM / C++ 工程的落点

- **基本类型偏执**：时间戳、像素坐标、世界坐标、四元数分量到处用裸 `double`/`Eigen::Vector3d` → 易把不同坐标系/单位的量混算。给关键量包一层带坐标系标签的类型（如 `PointInCam` / `PointInWorld`），编译期挡住跨系相加。
- **数据泥团**：相机内参 `fx,fy,cx,cy` 总结伴传 → `struct Intrinsics`；位姿 `R,t` → 一个 `Pose` 类型。
- **重复的 switch**：按 sensor 类型 / factor 类型分支的 switch 散在前端多处 → 多态化，新增传感器只加一个子类。
- **全局数据 / 可变数据**：标定参数、全局配置单例随处可改 → 封装变量 + 收窄作用域，避免「改了一处、另一处行为悄悄变」。
